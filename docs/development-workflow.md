# 共通AI開発ワークフロー

運用版：v1.1（2026-10-22）。各プロジェクトの採用範囲・適用開始点は、その既存の運用設定に記録する。製品仕様の版とは独立して管理する。

Terra Lifeでの採用・適用開始点・固有ルールは[project-context.md](project-context.md)第9章を参照する。旧v1.0の基本運用・裁量方針の採用記録は同書に保持し、経路・レビュー・Git担当・モデル選択の現行規則は本版を適用する。

## 1. 通常の進め方

目的・変更範囲・受入条件・必要な参照資料が揃えば、ユーザー、Chat、既存タスク文書からCodexへ直接依頼する。Workによる指示書の再生成は必須にしない。

1. 今回の目的、範囲、期待する結果を定め、AIが影響・不確実性を短く確認する。
2. 許可範囲をCodexが実装・自己検証する。計画を提示するためだけに再承認待ちにしない。
3. リスクに応じた独立レビューを行い、必要な指摘を統合して修正・再検証する。
4. ユーザーが結果と残課題を確認し、受入れを判断する。
5. 通常のcommit・pushはユーザーが行う。次の作業は依頼済み範囲に従う。

Workは、仕様の矛盾整理、未決事項の比較、複数資料をまたぐ調査、複雑な設計、工程分割、進捗の横断確認、独立レビューに追加の価値がある場合に使う。既存の短い依頼を長いプロンプトへ変換するためだけには使わない。

## 2. 役割・権限・正本

| 担当 | 責任 |
| --- | --- |
| ユーザー | 仕様・例外の採否、受入れ、次工程の依頼、通常のcommit・push |
| Chat | 相談、学習、初期検討、明確なタスクの依頼文、必要時のレビュー統合 |
| Work | 必要な調査・計画・文書整備・進捗確認・設計検討・独立レビュー |
| Codex | 許可範囲の実装・修正・検証・変更の報告。複雑なGit問題の分析 |
| 独立レビュアー | 仕様・コード・根拠の照合。実装者の自己評価と別の結果を提出 |

仕様決定権はユーザーにある。未決・提案・暫定・採用済みを区別する。命名、関数分割など仕様を保つ技術判断は実装担当に委ねる。暫定値は明示的に委任された項目・制約内で選び、暫定であることと理由を記録する。

仕様、受入条件、公開契約、保存互換性、主要依存、利用者体験の変更は、理由・影響を提示して採用指示を得る。既にその変更を依頼されている場合は再承認不要。範囲内の修正を逐次承認待ちにせず、関係のない未決事項で許可済み作業全体を止めない。

正式な共有・変更履歴の保存先はGitHub。ローカル未commit・commit済み未push・push済みを区別する。最新の明示的なユーザー指示は対象範囲で適用し、確定事項を正本文書へ反映する。会話だけを正本にしない。

| 情報 | 管理する場所 |
| --- | --- |
| 共通の手順・リスク・モデル選択・Git担当 | 本書 |
| 独立レビューの資料・独立性・統合 | [independent-review-policy.md](independent-review-policy.md) |
| AIが毎回守る短い境界・参照先 | リポジトリのAGENTS.md |
| 仕様版・現在地・コマンド・担当・採用例外 | 既存のproject-context／開発計画など、プロジェクトの正本1つ |
| 今回の目的・受入条件・結果 | 既存タスク記録。軽微なら短い作業記録で可 |

本文を複製せず参照する。AGENTS・Project指示には作業境界を短く再掲する。参照先が読めない相手には必要な抜粋・資料を渡す。リンクだけで確認済みとしない。矛盾があれば該当箇所を特定し、明示された採用差分で解けない部分だけ判断を求める。既存AGENTSや配下の指示をテンプレートで丸ごと置換しない。

## 3. リスクとレビューの選択

AIは着手時に「失敗の影響」と「実装・検証の難しさ」を確認する。採点表は毎回作らず、区分と理由を1行で示せばよい。

見る点は、アルゴリズム、依存関係・波及範囲、仕様整合性、状態管理・非同期・競合、DB移行・データ損失、認証・認可、回帰、未決仕様、検証困難性。行数・ファイル数・担当モデルだけで区分を決めない。

| 区分 | 判断の目安 | 基本の確認 |
| --- | --- | --- |
| 軽微 | 挙動不変の文言・局所表示など。影響が限定され、容易に確認・復旧できる | Codexの自己検証＋ユーザー確認。独立レビューを省略可 |
| 通常 | 要求と境界が明確な機能追加・修正。影響を特定でき、対応する検証が可能 | 自己検証。共有契約・失敗経路・確認不足などに応じ単独の独立レビュー |
| 重要 | データ損失・他人のデータ露出、主要な保存契約・権限境界、複雑な競合、広い回帰、重要な中核処理で検証が難しい変更 | 自己検証＋二重の独立レビュー。両プロジェクトの初期候補はWork Astra＋Claude |
| 設計検討が必要 | 重要な変更のうち、要求や設計の選択が未解決で、実装後の手戻りが大きい | 実装前の設計レビューを追加。仕様はユーザーが決定し、実装後の確認も行う |

重要機能のファイルに触れるだけでは「重要」にしない。一方、権限条件の1行変更でも影響が重大なら重要として扱う。局所的な修正であるという理由だけで高いリスクを軽視しない。

重要な変更の二重レビューを、利用枠の不足だけで黙って省かない。代替レビュアー、延期、範囲縮小、追加検証付き単独レビューを提案し、例外はユーザーが残るリスクとともに判断する。Claudeそのものを全タスクの必須工程にはしない。

進行中タスクで約束済みのレビュー条件は保持する。変更するなら対象と理由を明示する。過去の受入済み作業を新ルールだけを理由に再レビューしない。

## 4. 環境・モデル・Effortの判断

通常の実装・文書作業はSol 6.1／Mediumを運用上の基準にする。現在の設定で十分なら継続する。これはモデル性能の絶対順位や各環境の設定保証ではない。

| 作業 | 推奨の出発点 | 選ぶ理由・調整 |
| --- | --- | --- |
| 相談・学習・初期案 | 現在のChatモデル／通常設定 | 資料・ツールが足りれば切替不要。Effort未提供なら「設定不可／通常設定」 |
| 明確な小修正 | Codex Sol 6.1／Low相当 | 影響が小さく確認方法が明確な場合。UI表示がLight等なら実際の名称を使う |
| 通常実装・原因が絞れた修正 | Codex Sol 6.1／Medium | 実装とテストを一続きで行える |
| 調査・仕様整理・複数文書の整合 | Work Sol 6.1／Medium | 資料をまとめる追加作業がある場合 |
| 複雑な実装・競合分析 | Codex Sol 6.1／High、またはAstra／Medium〜High | 問題の難しさ・未解決点・利用枠から選ぶ。順番に全設定を試す義務はない |
| 難しい設計・重要な独立レビュー | Work Astra／Mediumを候補。複雑な経路・複数の競合する仮説ならHigh | 重要度だけで最高Effortへ固定しない。明確な限定確認ではLow相当も可 |
| 特に難しい未解決問題 | 対応モデルのExtra High／Max相当を検討 | 範囲・資料・再現条件を整えても深い分析が必要で、追加消費に見合う場合だけ |

提案する場面は、新タスク開始、環境をまたぐ引き継ぎ、当初より大きな難易度・リスクの発見、重要な設計・レビューの開始。新タスクの初回は1行で示し、同じタスクの毎回答では繰り返さない。ユーザー指定にも不足があると判断したら理由を示して再提案する。

推奨文の型：
> 推奨：Codex（GPT-6.1 Sol／Medium）。要求と変更境界が明確で、通常の実装・テストが中心のため。レビュー：単独を推奨（共有処理への影響を確認）。

レビュー人数とEffortは別に選ぶ。高いEffortでも検証、独立性、ユーザーの仕様判断を代替できない。詰まったらまず不足資料・再現手順・タスクの大きさを直し、必要に応じて設定を上げる。解決後に戻す場合も切替・引き継ぎの手間を考慮する。

実際に選べるモデルと設定を優先する。未確認の設定、Claude等とのEffort対応、利用残量、料金を断定しない。ユーザーが選択・変更する前提とし、「変更した」と装わない。別の選択肢を提案する場合も、改善する点と切替負担を短く示す。

## 5. 指示・記録を短く保つ

タスクは「目的と受入条件を一緒に確認できる単位」。軽微な作業では新規の指示書を不要とし、目的・範囲・受入条件・参照の数行でよい。通常作業も既存タスクを直接指定できる。複雑な作業に限り、未決事項、依存、検証計画、停止位置を補足する。

同じ規則を毎回貼らず、[task-handoff-templates.md](task-handoff-templates.md)から必要な型だけ使う。ただし受け手が共通ルールを読めない場合、権限・禁止事項・重要な受入条件は省かない。

作成する報告は、変更点、受入条件の結果、検証コマンドと実際の結果、未実施・残課題、レビュー状況、Git状態を中心にする。長いログは必要部分へ参照。事実と自己評価を分け、同じ内容をChat・Work・タスクへ別々に書き直さない。

タスク状態は準備中／作業中／ブロック中／受入待ち／完了を基本とし、レビューとGitの状態は別に持つ。既存の状態名を移行のためだけに改名しない。受入れ前は受入待ち、本人の受入れ後に完了。軽微な作業は既存記録1行でよい。commit番号を全資料へ転記するためだけにAIを呼ばない。

## 6. 検証・受入れ・Git操作

変更で起き得る失敗に対応した検証と、プロジェクトの必須チェックを行う。低影響の文言修正に形式的な新規テストは不要。失敗を消すために期待値を根拠なく変えない。提供されたログと自分で実行した結果、成功・失敗・未実施・環境制約を区別する。

受入待ちの条件は、範囲と受入条件の充足、必要な検証・レビュー、採用指摘の解消、残る制約の明示、対象変更の識別。未達の必須条件はブロック中または条件付き受入れの提案とし、ユーザーが判断する。

**通常のcommitとpushはユーザーがVS Codeまたはターミナルで実行する。** 操作専用のAI依頼・プロンプト・確認会話は原則不要。

- 実装終了時にCodexが今回の変更・未追跡ファイル・検証状況を既存の完了報告へまとめる。
- commit前にユーザーが、作業ブランチ、変更一覧、staged／unstagedの差分、未追跡、削除・改名、秘密情報や不要物の混入、検証・レビューの対象一致を確認し、commitする範囲を選ぶ。
- レビュー後にコード・設定・テストが変われば、影響範囲の再検証・再レビューを行う。記録文書だけの追記は内容を確認し、変更一覧へ残す。自動的な全面再レビューは不要。
- push前にユーザーが、送信先・ブランチ・送るcommit・自動処理への影響を確認し、pushするか判断する。commitはローカル記録、pushはリモート反映として分ける。
- 受入れ済みでも、commit／push／deploy済みとは扱わない。pushで自動deployが走る構成はプロジェクト設定に記載する。AIへpushを依頼する場合は、その副作用も含む明示指示を必要とする。
- Gitの競合・履歴修復などはCodexに調査を依頼できる。調査依頼から履歴改変・force push・変更破棄の許可を推測しない。
- AIによるcommit・push・merge・deploy、履歴改変、リモート設定／データ更新・外部公開は、操作と対象を含む明示指示がある場合のみ。許可済みの同一操作の再承認は不要。

確認はVS Codeの差分表示でもよい。チェック結果を毎回スクリーンショットでAIへ送る義務はない。Git履歴から取得できる情報を多重に管理しない。

## 7. 定型作業の省力化

まず既存のpackage scripts・タスクランナー・VS Code・Gitの機能を利用し、繰り返し負担がある部分だけスクリプト化する。新しい管理サービスや専用台帳は増やさない。

| 作業 | 第一選択 | 自動化するなら守ること |
| --- | --- | --- |
| 差分・未追跡確認 | VS Code／既存Git表示 | 未追跡やignoreで隠れた必要ソース、削除・改名も確認 |
| テスト・Lint・型確認 | 実在確認済みの既存コマンド | 各終了状態を保持。失敗をログ収集処理の成功で隠さない |
| 検証記録 | 実装中の実行結果を一度まとめる | コマンド・環境・結果・対象ID。秘密値を収集しない |
| レビューZIP作成・整合性確認 | 既存の安全な作成手順を再利用 | 対象の固定、一覧照合、ハッシュ、除外理由、展開確認。詳細はレビュー方針 |
| 意見の統合・未知の不具合分析 | AI | コード・仕様・再現証拠に基づく判断が必要な部分へ集中 |

ZIP化はスナップショットを固定して行い、作成中に対象が変わればやり直す。収録候補を明示し、秘密情報の単純な文字列検出だけで安全を保証しない。必須資料の漏れや不一致を発見したら成功扱いにしない。Gitへの書込み・リモート接続を定型収集へ混ぜない。

導入前に「既存手段で十分か／何回繰り返すか／誰が保守するか」を短く確認する。今回は自動化の提案までで、スクリプトの導入は別タスク。2〜3タスク後に引き継ぎ回数・待ち時間・手戻りを簡単に振り返り、使わない手順を減らす。正確なトークン節約量の計測は必須にしない。

## 8. 公式情報と運用判断の区別

2026-10-22確認：[Models](https://learn.chatgpt.com/docs/models)、[Model selection](https://learn.chatgpt.com/docs/model-selection)。

公式資料では利用できる設定がクライアント等で異なり、Effortの意味もモデル世代間で完全には一致しないと説明されている。Light／Low等の実表示を優先する。Astraにも低いEffortから始める案内があり、本書の「重要レビューはMediumを候補」はこの開発運用の判断であって公式必須値ではない。

本書のリスク区分・役割分担・レビュー基準はユーザーの開発向けに設計した運用方針。利用枠の数値や特定モデルの品質保証は含まない。
