# 共通AI開発ワークフロー

- 運用版：v1.0（2026-10-17）
- 状態：基本運用は採用済み（project-context.mdのD01・D02）。個別の仕様・工程細目・実装範囲は、タスクごとの採用判断と依頼に従う。
- 個別設定：[project-context.md](project-context.md)
- 記入型：[task-handoff-templates.md](task-handoff-templates.md)

## 1. 役割と責任

| 担当 | 責任 | 初期の環境・モデル選択 |
| --- | --- | --- |
| ユーザー | 目的、仕様の採否、許可範囲、結果の受入れ、次工程への移行 | 本人 |
| 相談担当 | アイデア、学習、選択肢の比較。確定と提案の区別 | Chat GPT-6 |
| 計画担当 | 資料確認、未決事項整理、タスク・受入条件・引き継ぎの作成 | Work Sol 6.1。複雑な設計はWork Astra |
| 実装担当 | 許可範囲の実装・修正、検証、証拠と未確認事項の報告 | VS Code／ローカルCodex Sol 6.1。難しい分析・実装はCodex Astra |
| レビュー担当 | 対象コードと要求を独立に照合し、問題と残る不確実性を報告 | Work。通常はSol 6.1でも可、重要な設計判断はAstraを候補にする |

この表は運用上の初期設定であり、モデルの絶対的な優劣や利用可能性を示さない。Workでしか計画できない、Codexでしかレビューできない、という制約も置かない。

独立レビューでは、当該変更を実装していない別の会話・作業コンテキストから、同じ仕様と対象コードを確認する。同じモデルでもよい。モデルの変更だけで独立性が成立するわけではなく、同一会話で実装者が再確認した場合は自己レビューと報告する。独立レビューも不具合ゼロの証明ではない。

## 2. 正本と参照の規則

正式な共有・変更履歴の保存先はプロジェクトのGitHubリポジトリとする。ローカル未commit文書・レビュー用ZIP・会話上の指示は、未反映の作業状態として識別する。GitHubへ未反映の状態を反映済みとは書かない。

| 情報 | 正本 | 他文書へ載せるもの |
| --- | --- | --- |
| 製品・ゲームの挙動 | 特定版の仕様書と承認された変更記録 | 版・節・変更記録への参照 |
| 作業ルール | AGENTS.md、採用した本workflow | 短い要約と参照 |
| 現在地・工程・参照先 | project-context、または既存の開発計画 | タスクIDと必要な抜粋 |
| 今回の範囲・受入条件 | 個別タスク／軽微な依頼の記録 | 対象タスクへの参照 |
| 実施結果 | タスク内の実装・検証・レビュー記録 | 状態と結果への参照 |

最新版という名前だけで選ばず、承認状態と適用版を確認する。仕様書中の「提案」「調整値」「保留」を維持し、文書全体の採用と個々の提案の承認を混同しない。

最新の明示的なユーザー指示で承認された差分は、その範囲で適用し、正本文書への反映状況を記録する。変更前の記録は消さず、失効・置換の関係を残す。指示の解釈が複数ある場合だけ該当箇所の判断を求める。タスクやAIの説明だけで仕様を上書きしない。

## 3. 作業の重さを決める

変更行数ではなく、失敗時の影響、戻しやすさ、仕様の曖昧さで分類する。複数に当たる場合は重い方を使う。途中で影響が広がったら分類を見直す。

| 区分 | 例・条件 | 最小手順 | 記録・レビュー |
| --- | --- | --- | --- |
| 軽微 | 意味を変えない文言、局所的な表示調整、挙動不変の小整理。保存・権限・公開契約等に影響しない | 本人→Codex→結果確認 | 目的・範囲・確認結果を短く残す。独立レビューは省略可 |
| 標準 | 境界の明確な機能追加・不具合修正、複数ファイルの整合変更 | 必要ならWorkで準備→Codex→本人確認 | タスク記録と対象検証。受入れ時に独立レビュー要否を明記 |
| 重要 | データ消失、保存形式、認証・権限、重要な状態遷移・時計・乱数、広範囲の設計変更、要求の重大な曖昧さ | 設計判断→実装・検証→独立レビュー→修正確認→本人受入れ | 原則、独立レビューを完了条件とする。例外は本人が理由・代替検証・残るリスクを承認 |

独立レビューを省く判断は、実装者の「問題なし」だけを根拠にしない。重要でない節目では、工程末の短い受入確認でよい。小さな変更でも公開・外部更新の許可要件は変わらない。

## 4. タスクの作り方と進め方

タスクは「1つの目的と受入条件を説明でき、結果を確認できる単位」にする。工程全体が大きければ分割する。先の工程を固定的に細分化しすぎず、次に着手する範囲から具体化する。

1. **準備**：適用仕様、対象コード状態、目的、範囲外、受入条件、検証、未決事項、権限を記録する。仕様不足がある場合は、実装タスクではなく調査・判断整理を先に依頼する。
2. **着手**：実装担当が実ファイル・作業ツリー・既存ルールを確認する。相違がなければ許可範囲の実装と検証を進める。計画を示すためだけに再承認待ちにしない。
3. **実装・自己検証**：影響範囲を確認し、必要な修正をまとめる。目的外の整理や将来機能を混ぜない。
4. **独立レビュー（必要時）**：対象を固定し、仕様適合・失敗経路・検証不足を確認する。重大な発見は修正方針とともに返す。
5. **修正・再検証**：依頼済み範囲内の不具合は許可に沿って修正し、変更箇所と影響範囲を再確認する。仕様変更が必要なら判断へ戻す。
6. **受入れ**：ユーザーが結果と残課題を確認する。タスク状態を更新し、次タスクの依頼があれば進める。実装完了から次工程への許可を推測しない。

既に複数タスクの連続実行を明示的に許可されている場合は、その境界まで進めてよい。無関係な未決事項のために、独立して実行できる許可済み作業全体を止めない。

## 5. 裁量と承認

| 判断・操作 | 扱い |
| --- | --- |
| 既存仕様を保つ命名、関数分割、局所的な実装方法、必要な範囲のテスト修正 | 許可されたタスク内で実装担当が判断。重要な理由だけ記録 |
| 暫定的な数値・案の試行 | タスクで委任された項目・制約の範囲のみ。値、理由、見直し条件を残す。正式採用に昇格させない |
| 仕様・受入条件、公開API、保存互換性、主要依存・技術基盤、利用者体験を変える判断 | 変更案と影響を提示し、採用の明示指示を待つ。既に当該変更を依頼されていれば再承認不要 |
| タスクに必要な既存依存の利用・通常のセットアップ | 作業環境と既存方針の範囲で実行可。新たな外部サービス契約や秘密情報の変更は含めない |
| 関連ファイルの追加・変更 | 範囲内で可。厳密な変更許可リストがある場合は従い、追加が必要なら相談 |
| commit・push・merge・deploy、履歴改変、リモート設定／データ変更、外部公開、秘密情報の設定・変更 | 操作と対象を含む明示指示が必要。push許可からdeploy許可を推測しない |
| 他人・他タスクの変更の破棄、テストを通すための根拠のない期待値変更 | 行わない |

「そのタスクを実装して」は、提示された範囲内のローカル実装・検証の許可とする。「よさそう」のような曖昧な返答だけから、外部操作や新しい工程の許可を拡張しない。許可済みの操作・対象が変わらない限り同じ確認を繰り返さない。

仕様変更の記録は「日付／論点／提案内容／理由・影響／状態／承認の根拠／反映先」で十分。状態は提案・採用・保留・却下を区別する。許可範囲内の技術判断は「実装判断」と記録し、ユーザー承認済みの仕様と区別する。

## 6. 検証と完了条件

検証は変更で起き得る失敗に対応させる。既存の必須チェックは守り、対象の小テスト→関連する統合確認の順に必要な範囲で実施する。低影響の文言変更等に、内容をなぞるだけの新規テストを義務付けない。

各タスクは次を満たした時点で「受入待ち」とする。

- 指定範囲と受入条件を満たす変更がある。各条件に確認結果が対応している。
- 必要な検証の実行環境・コマンド・結果が記録されている。未実施・失敗・環境要因が区別されている。
- 必須レビューが完了し、進行を妨げる指摘が解決したか、本人が例外を承認した。
- 残る制約・未検証・判断事項、変更した仕様参照・タスク状態が記録されている。
- 対象外の変更を混ぜていない。GitHub反映状況とコード状態が識別できる。

検証不能なら「ブロック中」または「条件付き受入れの提案」とし、完了を装わない。本人が残る不確実性を了承して受け入れる場合は、その条件を記録する。ユーザー受入れ、commit、push、deployは別の状態であり、commitしていなくても受入判断は可能。

## 7. 独立レビューの渡し方

コードをレビューする前提は「何をレビューしたか」が分かること。GitHub上のHEADがローカル未commitの実装と同じとは限らない。

| 対象 | 引き渡す識別情報 |
| --- | --- |
| commit済み | リポジトリ、比較元・対象の完全なcommit SHA、差分、適用仕様・タスク |
| 未commit | 基準SHA、作業スナップショットID、変更後ファイル、staged／unstaged／未追跡を含む差分・一覧、削除・改名情報 |
| Git初期化前・初回commit前 | 基準commitなしと明記し、対象ファイル一式とスナップショットID |

スナップショットは日付付きIDとファイル一覧を持たせ、ZIPのSHA-256またはファイルごとのハッシュで固定する。関連する変更前コード・呼出し元・型・設定・テストも読めるようにする。差分だけで判断できない場合は必要な周辺ファイルを追加し、不足を明示する。秘密値、個人データ、不要な依存フォルダや生成物を含めない。

レビュー担当は先に要求とコードを確認し、実装者の自己評価と照合する。実行した検証と提供されたログを区別する。静的に読んだだけなら「静的レビュー」、テストを実行した場合はその範囲を併記する。

指摘はID、重大度、場所、根拠、再現条件または推論、影響、修正方向を含める。「重大（進行停止・消失等）／通常（仕様逸脱等）／軽微（読みやすさ等）」を基本とし、確定指摘・疑い・任意改善を区別する。好みだけの提案を受入れの阻害要因にしない。誤った指摘は根拠付きで不採用にできる。

修正後は新しい対象IDを付け、旧レビューから変わった部分と影響範囲を再確認する。以前のレビューが新しい差分を承認したとは扱わない。変更が限定的なら全面レビューの反復は不要だが、重要な問題の解消はレビュー担当が確認する。重大な設計変更なら広い範囲を再レビューする。

## 8. 進捗・利用枠・運用負担

タスクの状態は「準備中→実行可→作業中→受入待ち→完了」を基本とし、途中の「ブロック中」とレビュー状況を別欄で記録する。実行可への変更は本人の依頼に基づき、完了は本人の受入れに基づく。Git状態は未commit・commit済み・push済み等を別記する。

モデル変更は、未解決の問題を短く言語化できた時に行う。まず不足資料・再現条件・依頼範囲を確認し、それでも複数の設計が競合する、原因が絞れない、同じ失敗が続く場合にAstraへ分析を渡す。解決方針が定まったら通常の実装はSolへ戻してよい。

- 利用枠の数値や「必ず安い・速い」という前提を文書へ固定しない。必要な場合に、その時点の表示と公式情報を確認する。
- 長い会話全文の移送より、仕様版・タスク・差分・未決事項を渡す。受け手が参照先にアクセスできるかも確認する。
- 初回に全体を読んだ後は、変わった箇所と必要な周辺を再確認する。仕様や対象コードの同一性が不明なら再取得する。
- 同じ内容の二重実装・無目的な複数モデル照合を通常運用にしない。
- 2〜3タスク運用してから、引き継ぎ時間、差し戻し理由、検証漏れを短く振り返る。使わない欄や重複記録を減らす。

## 9. AGENTS導入時の注意と出典

既存AGENTSを優先して内容を確認し、共通テンプレートを丸ごと上書きしない。グローバルや下位ディレクトリの指示も確認する。公式資料では、Codex CLIはグローバルおよびリポジトリから作業ディレクトリまでの指示を読み、深い位置の指示を後に適用すると説明されている。テンプレートのファイル名や別文書へのリンクだけで自動読込が保証されるとは扱わず、実際に適用される参照先を確認する。
