# 開発タスク・引き継ぎテンプレート

運用版：v1.2（2026-10-23）。判断規則は[共通ワークフロー](development-workflow.md)、レビュー手順・利用量削減方針は[独立レビュー方針](independent-review-policy.md)。

必要な型だけ使い、既存タスクがあれば直接参照する。共通指示を読める相手には繰り返さない。読めない相手には作業境界と必要な資料を添える。空欄を埋めるためのAI呼出しは不要。

## 1. 実装・修正の短い依頼

```markdown
目的：<今回達成したいこと>
範囲：<対象、守る挙動、必要なら範囲外>
受入条件：<観測できる結果>
参照：<既存タスク／仕様版・節／実ファイル>
```

依頼先に共通ルールがなければ「上記範囲のローカル実装・検証のみ。仕様変更は提案。commit・push・deployなし」を補う。

AIは着手時、必要に応じ次の1行を添える：
`推奨：Codex（Sol 6.1／Medium）。理由：…。リスク：通常。レビュー：なし／単独／二重（理由）。`

すでに十分なタスク文書がある場合は「<タスクパス>の指定範囲を実装・検証してください」でよい。参照できること、今回の着手許可、受入条件が明確であることが前提。

## 2. 複雑なタスク・Workへの検討依頼に追加する欄

```markdown
成果物・停止位置：<設計案／実装／レビューなど>
採用済み／提案・保留：<区別して記載>
基準コード・既存変更：<SHA／確認済み状態。未確認なら明記>
依存・未決事項：<着手を阻むもの／後回しにできるもの>
重点リスク・検証：<具体的な失敗条件と確認方法>
裁量：<委任する暫定値や設計判断があれば>
レビュー：<方式・担当・統合担当。参照で代用可>
```

Chat→Work専用の別文書を必須にしない。「目的・依頼する成果・採用済みと保留・資料・範囲」が渡ればよい。仕様書を読まずに会話要約を確定仕様へ昇格させない。

## 3. 実装完了・中断の報告

```markdown
対象：<タスク、仕様版、コード状態>
変更：<内容と主要ファイル。新規／削除／改名・対象外変更も識別>
受入条件：<達成／未達／未確認と根拠>
検証：<実行コマンド・環境・結果。未実施は理由>
残課題：<制約・必要な判断。なければなし>
レビュー／Git：<自己検証のみ等、未commit等。確認できた事実>
次の状態：<受入待ち／ブロック中。必要な次の行動>
```

複数条件がある場合だけ表にする。対象の細かなファイル一覧・ログは参照でよい。中断・担当変更時には「止まっている問題／再現方法／試したことと結果／次の許可済み作業」だけ追加する。会話全文は移送しない。

## 4. レビュー資料作成・共通依頼・担当別条件

### 資料作成の依頼

```markdown
対象：<タスクID／コードsnapshot ID／基準commit SHA／対象ファイルとハッシュ>
配布：<配布資料版。再構成時は新版とし旧ZIPを保持>
同じスナップショットから初回資料と必要時の補足を作成してください。
構成・除外・整合性確認は独立レビュー方針第2節に従ってください。
入口：<目的・範囲・受入条件・読む順序・関連ファイル・既知の制約>
初回：<変更後コード原文・必要な周辺コードと関連テスト・仕様・読解用差分・短い検証一覧・判断に必要な成功／失敗の証拠>
初回に未収録の範囲／補足：<内容・参照方法。少量なら単一ZIPで可>
作成結果：<収録漏れ・ハッシュ・差分・展開後整合性の結果と不一致>
配布識別：<資料版／各ZIP名・SHA-256。コード識別とは別記しZIP外に提示>
```

### 共通レビュー依頼（双方へ同一本文）

```markdown
添付ZIPの対象を独立レビューしてください。
コード対象：<タスクID／snapshot ID／基準commit SHA／対象ファイルハッシュの参照先>
配布資料：<資料版／初回ZIP名・SHA-256／補足の版・内容・参照方法>
正本：ZIP内worktree/。適用仕様・受入条件：<ZIP内の参照先>
目的・確認範囲・重点観点・読む順序：<入口資料の参照先>
既知の制約・未収録範囲：<失敗・原因未確定・未検証・計装や実行条件の違いを含む中立的な事実>
参照：ZIP内の独立レビュー方針（なければ必要な指示を添付）。
他方の結果や開発側の評価を参照せず、仕様・コード・検証記録から評価してください。
コード変更・commit・push・deploy・リモートDB操作は禁止です。
実行条件：共通の確認範囲を保ち、下記の担当別条件を適用してください。
追加の仕様・コード・検証資料は双方へ同じものを共有し、判断に用いた版を記録します。
両者の初回結果が揃うまで、互いの指摘・結論・統合案は共有しません。
報告：下記の簡潔な初回報告の型。資料不足や利用上限による未完了は判断保留としてください。
原本ZIPを変更せず、初回結果を別ファイルに保存してください。
```

レビュー用の環境・モデル・Effort提案は、配布本文の外でユーザーへ示す。Work向けの設定をClaudeへそのまま要求しない。共通手順を参照できなければ、初回結果を他方へ見せないこと・不足資料を推測しないことを本文に補う。

### 担当別の実行条件（該当担当へ添付）

```markdown
Work：静的レビューと提供検証記録の照合。必要時のみ、許可した隔離環境で対象を絞って実行。
許可した実行検証：<環境・対象・コマンド／指定なしなら実行前に条件を確認>
全テスト再実行・環境構築は毎回必須ではありません。環境制約は未実施と記録し、修復を目的化しないでください。
```

```markdown
Claude：静的レビューと提供検証記録の照合を基本とします。依存インストール・環境修復・全テスト再実行は行わないでください。
既存環境でのZIP展開・ハッシュ照合・差分比較は可能です。整合性確認は可能なら一括処理し、結果と不一致を報告してください。
変更後コードを中心に必要な比較・依存先へ広げ、全ファイル一括表示・反復読解・不要な外部検索を避けてください。
動的確認が必要な疑いは、発生条件・コード上の根拠・最小限の確認方法を報告し、推測で不具合確定や検証済みにしないでください。
```

### 簡潔な初回報告

```markdown
対象：<コードsnapshot ID／基準commit／判断に用いた配布資料版・ZIPハッシュ>
確認範囲・資料整合性：<確認した範囲／未完了範囲／照合結果・不一致>
指摘：<ID・場所・発生条件・影響・根拠・重大度・確度・修正方向。なければなし>
検証：<自分で実施した内容・結果／提供記録との照合／未実施と理由>
未確認・受入れに関わる未解決点：<必要な追加資料や最小限の動的確認>
判定：<受入れ可の意見／修正後に受入れ可の意見／資料・検証不足で判断保留>
```

問題のない領域の長い解説や全ハッシュの表示は不要。重大な指摘の件数は制限しない。判定はレビュアーの意見で、最終受入れはユーザーが行う。

## 5. 統合・修正・受入れ記録

| 統合ID／原指摘ID | 根拠・再現結果 | 重大度 | 処置・理由 | 修正後の対象と確認 |
| --- | --- | --- | --- | --- |
| I01／A-01・B-03 | 仕様・コード・テスト | 重大／通常／軽微 | 採用／不採用／追加検証／保留 | snapshotと結果 |

既存タスクへ追記し、同じ台帳を増やさない。修正依頼は「採用ID、守る挙動、修正範囲、必要な再検証」を渡す。生の相矛盾する報告をそのまま両方実装させない。

初回結果提出後の追加検証は、統合担当からWorkまたはCodexへ「対象ID・資料版／疑いと根拠／発生条件／最小限の確認方法／結果の共有先」を渡す。Codexの結果は実装側検証と記録し、Claudeの独立再実行に数えない。修正後の局所的再確認は原則1名とし、新しい重要変更・広い設計変更があればレビュー方式を再評価する。

受入記録は `日付／ユーザー判断／対象ID／残課題・例外／次の依頼範囲` でよい。AIが先回りして受入済みにしない。commit・pushはユーザー担当とし、Git操作専用の引き継ぎ文は作らない。

## 6. 既存の詳細タスク型を使う場合（任意）

プロジェクトの現在地と固有ルールは[project-context.md](project-context.md)を参照する。従来のdocs/tasks/<task-id>.md方式を継続できる。前半の依頼・受入条件を保持し、後半へ実装・レビュー・受入記録を追記する。指示・結果を別々の正本へ複製しない。

既存v1.0で必要だった詳細欄は、複雑なタスクで必要なものだけ維持する。短い依頼を、この型に埋め直すためのWork経由は要求しない。

| 欄 | 残す内容 |
| --- | --- |
| 状態・リスク・担当 | 既存の状態名（実行可を含む）、理由、環境・モデル・Effort、レビュー方式と統合担当 |
| 基準・許可 | 完全な基準SHA／基準なし、既存変更、着手許可の根拠、今回の権限と停止位置 |
| 範囲・裁量 | 含む／含まない、対象、厳密な変更許可リスト、依存・未決事項、委任する暫定値と制約 |
| 受入条件 | ID・観測する結果・確認方法、実在する必須コマンド／未設定の区別、重点リスク |
| 結果・受入れ | AC別の結果、実行環境・コマンド・終了状態、未実施・制約、指摘IDと処置、ユーザーの判断・残条件・次の許可範囲 |

受入条件を「テストが通る」だけにしない。期待する挙動と検証方法を対応させる。未確認・未決定・該当なしを区別し、利用しない欄は削除してよい。既存タスクの約束済みレビュー条件・受入記録はこの型への移行のために変更しない。
