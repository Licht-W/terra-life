# 開発タスク・引き継ぎテンプレート

- 運用版：v1.0（2026-10-17）／採用済みの基本運用に対応。記入例は個別仕様・工程細目・実装範囲の採用や許可を意味しない。
- 方針：[development-workflow.md](development-workflow.md)
- プロジェクトの現在地：[project-context.md](project-context.md)

必要な型だけ使う。すべてを毎回埋める必要はない。空欄は削除できるが、未確認・未決定・該当なしは区別する。参照先だけで渡す場合は、受け手が実際に読めることを確認する。既存のタスク文書は同じものを更新し、指示・報告・レビューを別々の正本へ複製しない。

## 1. 軽微な変更（Codexへ直接）

```markdown
目的：<直したいこと>
対象：<ファイル／画面／箇所。未確認ならその旨>
範囲外：<挙動変更や関連機能の追加等>
受入条件：<何を確認すれば完了か>
参照：<必要な仕様版・節。挙動不変ならその旨>
今回の権限：上記範囲のローカル変更と必要な検証。commit・push・deployなし。
完了時：変更点、確認方法と結果、未確認事項を短く報告し、作業記録へ要約する。
```

実装中に保存・状態遷移・仕様の変更へ広がる場合は、軽微のまま押し通さず、範囲とレビュー要否を見直す。

## 2. Chat→Work（決定・相談の引き継ぎ）

```markdown
# <プロジェクト> 引き継ぎ
今回依頼する成果：<仕様整理／比較／タスク作成等>
目的・避けたいこと：<短く>
採用済み：<ユーザーが採用した内容と根拠。なければ「なし」>
提案・保留：<未採用の案と残る判断>
参照資料：<実ファイル／版／URL。未添付や未確認は明記>
現在の実装状態：<確認済みの事実／未確認>
今回の範囲外：<実装や仕様の独断確定等>
```

会話中の「おすすめ」と本人の「採用」を分ける。記憶や要約から仕様書の現在の本文を確認済みとしない。

## 3. Work→Codex（標準・重要タスク）

以下を`docs/tasks/<task-id>.md`等の1ファイルに置き、後半へ実装報告とレビューを追記する。

```markdown
# <task-id> <成果を表す題名>

- 状態：準備中／実行可／作業中／ブロック中／受入待ち／完了
- リスク：標準／重要（理由：<失敗時の影響>）
- 実装担当：<環境・モデル。未指定可>
- レビュー：不要／必要・未実施／確認中／完了（理由・対象ID）
- 適用仕様：<ファイル・版・節、採用済み変更記録>
- 基準コード：<リポジトリ・ブランチ・基準SHA、または未作成>
- 既存変更：<未commit変更の有無・所有範囲、または未確認>
- 着手許可：<日付・本人の依頼の要約。未承認なら明記>

## 目的と範囲
目的：<利用者または開発上の成果>
含む：<今回扱う処理・機能>
含まない：<次工程・目的外の作業>
変更対象：<目安のディレクトリ等。厳密な許可リストなら明記>
依存・前提：<先行タスク・資料・環境>
未決事項：<着手前に必要な判断／後回しにできる判断>
裁量：<自由に選べる実装方法、委任する暫定値と制約>

## 受入条件と検証予定
| 条件ID | 期待する観測可能な結果 | 確認方法 |
| --- | --- | --- |
| AC1 | <入力・条件に対する出力や状態> | <テスト／手動確認等> |

必須コマンド：<実在確認済みのコマンド／未設定なら確認するタスクを明記>
重点リスク：<今回の不具合候補だけ>
独立レビュー：<要否・観点・予定担当>

## 許可と停止位置
上記範囲のローカル実装・検証、および受入条件内の不具合修正を許可する。
仕様変更・範囲拡張は提案し、採用指示後に反映する。
commit・push・deployは許可しない。完了時は受入待ちとして報告する。
次タスクは<未許可／明示的に許可された連続範囲>。

## 実装報告・レビュー・受入記録
<以下の様式から必要なものを追記>
```

受入条件は「テストが通る」だけにしない。期待する挙動と検証方法を対応させる。実際の依頼でGit操作を許可する場合のみ、許可欄を対象・操作・終了条件つきで変更する。

## 4. Codex→ユーザー／Work（実装報告）

```markdown
### 実装報告 <日付>
- 対象：<task-id、仕様版、コード／スナップショットID>
- 変更：<何をどう変えたか、主要なファイル>
- 実装判断：<理由が必要な技術選択、委任された暫定値>
- 自己確認：<受入条件IDごとの達成状況>

| 検証 | コマンドまたは手順 | 実際の結果 | 実行環境・制約 |
| --- | --- | --- | --- |
| <対象> | <実行内容> | 成功／失敗／未実施 | <必要な版・理由> |

- 残課題・未検証：<なし、または具体的な条件>
- レビュー状況：<未実施／自己確認のみ／独立レビュー対象ID>
- Git状況：<未commit／commit済み等。承認された操作だけ>
- 提案する状態：<受入待ち／ブロック中>
- 必要な判断：<残る仕様判断や例外受入れ。なければなし>
```

ログ全文は常に貼らなくてよい。再現に必要なコマンド・結果と、問題がある場合のログ箇所を残す。本人による受入れ前に「工程完了」と断定しない。

## 5. Codex→レビュー担当（独立レビュー依頼）

```markdown
# <task-id> 独立レビュー依頼
目的：<仕様適合・不具合・検証不足の確認>
許可：閲覧と必要な検証のみ。ソース修正・commit・push・deployなし。
対象仕様・タスク：<版・節・受入条件>
対象コード：<対象SHA、またはスナップショットIDとSHA-256>
比較元：<基準SHA／初回のため基準なし>
同梱物：<変更後コード・比較元・差分・設定・テスト・実装報告>
未追跡・削除・改名：<含め方と一覧>
重点観点：<リスクを3〜5項目程度>
既知の制約：<未検証環境・意図的な対象外>
成果物：<同じタスク記録への追記、またはレビュー結果ファイル>
```

レビュアーは対象資料が不足していれば不足部分を示し、確認済みの範囲だけを報告する。確認用の一時生成物が出る検証と、ソース修正は区別する。

```markdown
### 独立レビュー <日付・担当環境／モデル>
対象ID：<レビューした正確な対象>
確認範囲：<静的読解／実行した検証>

| ID | 重大度・確度 | 場所・条件 | 根拠・影響 | 修正方向 |
| --- | --- | --- | --- | --- |
| R1 | <重大／通常／軽微、確定／疑い／任意改善> | <ファイル・関数・再現条件> | <仕様節や確認結果> | <最小限の修正方針> |

受入条件の対応：<達成／不足／未確認>
結論：進行を妨げる指摘あり／確認範囲では該当指摘なし／資料不足で判断不可
未検証・残るリスク：<具体的に>
```

## 6. レビュー後の修正と受入れ

```markdown
修正対象：<R1、R2等>
今回の範囲：<既存の受入条件を満たす修正。新仕様があれば未承認と明記>
不要と判断した指摘：<ID・根拠。黙って無視しない>
修正後の対象ID：<新しいSHA／スナップショットID>
再検証・再レビュー：<指摘ごとの解消確認と関連範囲>
```

```markdown
### ユーザーの受入れ記録
日付：<日付>
対象：<task-id、コードID>
判断：受入れ／条件付き受入れ／差し戻し
根拠：<本人の明示指示の要約>
残課題・例外：<理由、代替検証、次に扱う時点>
次タスク：<未許可／許可した対象>
Git操作：<未許可／許可した操作と対象>
```

この記録をAIが先回りして承認済みとして埋めない。受入れとGit操作の許可を分ける。

## 7. 中断・モデル切替時の短い引き継ぎ

```markdown
対象タスクとコードID：<参照>
今できていること：<確認済みの事実>
止まっている問題：<期待と実際、再現条件>
試したこと：<方法と結果。失敗も含む>
未決・未検証：<必要な判断・不足情報>
次に行う作業：<依頼済み範囲>
権限と停止位置：<既存の許可範囲を維持>
```
