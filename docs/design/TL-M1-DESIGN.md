## 3. 出生とゲーム内時間（D02：採用）

- P01の国・種族は採用方針に沿ってヴィクトリア・フェリーンに限定する。家庭背景・基本値等の分布は検証用設定として区別する。
- 出生候補を扱うBirthDraftと、開始後のCoreStateを別の段階にする。再抽選はBirthDraftに対してだけ可能とし、開始後の出生は固定する。
- 開始時に、正規化シード、再抽選回数、選んだ出生条件、ルール・データ版、開始時乱数状態をOriginとして保持する。
- 0歳の春をseasonIndex=0とする。年齢はfloor(seasonIndex / 4)、季節はseasonIndex % 4から求める。年齢と季節を別々の更新値にしない。
- seasonIndexは季節完了時にだけ1増やす。冬の途中で死亡したら、その冬の年齢・季節で終わり、年末補充や加齢は行わない。
- 成長段階・身体の老化度は実年齢とは別の概念として持つ。検証で使うフェリーン用設定を差し替えられるようにし、原作の成人年齢・寿命として断定しない。
- フレーバーを含めてイベントがなかった季節は、人生記録に空の季節見出しや空欄を表示しない。イベントがある記録に年齢・季節を付ける。表示を省く季節も、内部の定期処理・抽選・季節更新は通常どおり行う。実画面はM2で実装する。

出生の再抽選で人生結果用の乱数を消費しない。同じ開始済みOriginからの実行に、開始前の画面操作や余分な候補表示を影響させない。

## 4. 状態と入力の案（D03）

途中位置の保持、二重適用防止、死亡成立後の打切りは採用済み。以下の入力API・revision・具体的な状態構造は、それを満たす設計案として区別する。

### 最小状態

実際の型名・ファイル名は後の実装判断とし、必要な情報と責務を先に定める。

| 情報群 | M1で保持するもの |
| --- | --- |
| Origin・版 | 開始条件、シード、出生履歴の識別、開始時乱数状態、ルール・データ・乱数方式の識別 |
| 人物 | 基本5値（健康・精神・資金・知識・人脈）、別管理の借金、必要な家庭環境・支援条件・職業・勤務地・現在地・活動状態、検証で使う状態・関係・フラグ、成長・老化情報。状況判定に必要な最小限を持ち、移動や家計全体を先行設計しない |
| 季節 | seasonIndex、処理段階、必須候補の残り、職業枠の確定予算と次の位置、当季節の定期収入の反映情報 |
| イベント | 発生インスタンスID、固定された定義・選択肢、選択方式、解決後の戻り先、即時連鎖キュー |
| 再発管理 | 季節内の表示済みID、発生回数、次回発生可能季節、将来の継続予約 |
| 結果・履歴 | 人生記録、選択記録、当年の通常記録件数、死亡情報または診断停止情報 |
| 乱数・入力管理 | 出生／人生結果／フレーバーの状態、人生イベントとフレーバーの別カウンター、revision |

進行状態は「通常処理可能／イベント提示中／死亡／診断停止」を区別する。イベント提示中には、選択なし・時限式・停止式の別を持たせる。死んでいるのに待機中などの矛盾を表現しにくい型にし、同じ事実を複数のisPaused・isDead等で二重管理しない。

手動停止・タブ非表示・復帰待ちと実時間の残量はM2のアプリ制御で扱う。M1のコアにブラウザ都合の停止フラグや時計を入れない。

### 純粋な遷移

1回のコア呼出しは、状態・入力・固定版のルール／データを受け取り、新しい状態と結果区分を返す。入力状態・定義データは書き換えない。React、DOM、Date.now、performance.now、Math.random、ブラウザ保存、外部I/Oには依存しない。

| 入力の案 | 意味 |
| --- | --- |
| Advance | 通常処理を1段階進める。提示済みの選択なしイベントなら解決する。選択待ち・死亡・診断停止を無理に進めない |
| Choose | 指定した人生・イベントインスタンスの、選択可能な行動を手動選択する |
| Expire | 指定した時限式インスタンスの既定行動を選ぶ。停止式には使えない |

入力には対象lifeIdとexpectedRevisionを付け、選択系にはeventInstanceIdも付ける。成功遷移でrevisionを更新し、同じ入力の再送や古いタイマー入力は不受理にする。Advanceの重複も、別の季節を勝手に進める入力として扱わない。

不受理は理由を返すだけで、人物・処理位置・乱数・revision・履歴を変更しない。再現用の選択記録には、インスタンスID・選択肢ID・手動／期限切れを残す。revisionや現実の待ち時間は意味上の再現入力にせず、リプレイ実行側がその時点のrevisionを使う。

M1では入力が与えられた順に解決する。実時刻での期限到達とクリックの優先規則はM2の判断として残し、「期限到達優先」を今回採用したとはしない。

### 中断・再開

処理段階・枠の位置・残りキュー・戻り先を状態に含める。「再開時に季節の先頭から処理をやり直す」という実装にしない。

状態はメモリ上でJSON往復できる値を基本とする。Date・Map・Set・関数・BigInt等を状態へ埋め込まない。M1の状態コピー検証は、M3の正式保存形式や互換性を承認するものではない。

## 5. 季節とイベント解決の案（D03・D06）

### 季節の基本経路

| 段階 | 処理と、再開位置に残す情報 |
| --- | --- |
| 開始 | 生存を確認し、年齢・季節・成長段階を整える |
| 定期処理 | 定期収入による資金増加→継続状態の変化→成長・教育等の変化→老化の順で、検証に必要な処理を当季節に一度だけ適用。各まとまりで死亡を確認し、生存なら次段階へ移る |
| 死亡確認 | 健康0や定義された直接死亡を確定。死亡なら以後を打ち切る |
| 必須・予約 | この段階に入った時点の対象を一度キュー化し、優先度→固定ID順で処理。各実行前に最新条件を再確認 |
| 共通生活 | 原則0〜1件。直前の職業・勤務地・現在地・活動状況で発生確率を補正し、矛盾する候補を除外。0%ならフレーバーへの代替も含めて当枠をスキップし、処理完了として記録 |
| 職業追加 | 段階入口で枠数を一度確定し、各枠を解決してから次へ。枠位置を保持 |
| 完了 | 生存中の冬で当年の通常記録0件なら中立フレーバーを補充し、seasonIndexを1増やす |

必須・共通・職業の各候補から、都度「提示→解決→即時連鎖」へ進み、その後に未処理の次候補・次枠へ戻る。全候補を先に抽選してからまとめて解決しない。

採用：必須・予約段階への入口で対象一覧を一度確定し、実行直前に最新条件を再確認する。先行イベントで不要になった対象は実行しない。途中で新たに条件が成立しても一覧全体を再走査せず、通常は次季節の対象とする。同季節に続けたい展開は、データに即時連鎖として明示する。連鎖の解決後は元の未処理位置へ戻る。例えば事故直後の治療選択は、明示的な即時連鎖として扱える。

職業枠から新規発生するイベントは、原則として各季節0〜1件とする。共通生活・継続イベントは別経路として扱い、職業枠の件数で人生記録全体の件数を制限しない。詳細は第6章。

### 提示・解決と死亡

- 発生時にID・本文・選択肢・結果定義を固定し、表示だけで結果分岐を抽選しない。
- 提示前に選択可能な行動が1件以上あり、時限式の既定行動も選択可能であることを確認する。
- 定義が固定されても、選択入力の対象・可否や支出条件は解決直前に再検証する。
- 選択なしも同じ解決経路を使う。時限式／停止式の結果抽選は、有効な解決入力を受けた時に一度だけ行う。
- **採用：結果の効果は定義順に適用し、健康0または直接死亡が成立したら、残る効果も含めて打ち切る。** 健康0の後に後続の回復効果で復活することは認めない。
- 正常な死亡は適用失敗ではない。死亡に至るまでの正常な効果を取り消さず、結果・死亡情報とともに確定する。データ不備による診断停止のロールバックとは区別する。
- 結果の乱数更新・効果・選択記録・人生記録・後続予約をひとまとまりの遷移として返す。明示借入・返済は、資金と借金の対になる更新を分割しない。
- 適用前の定義検証に失敗したら、部分的な効果や乱数更新を残さず診断停止する。死亡は正常なゲーム内結果、診断停止はデータ／プログラムの問題として区別する。
- 死亡情報と原因イベントを結び付け、一度だけ終了を記録する。死亡後は、枠・連鎖・冬の補充・加齢を実行しない。
- 定期処理も健康0・直接死亡の成立時に残る処理を止める。定期収入の反映を含む各まとまりの順序は固定する。生活費を定期徴収する段階は設けない。

## 6. 抽選・継続・職業枠（D06：基本規則を採用）

### 共通生活枠の状況補正（採用）

- 共通生活枠は職業専用枠とは別の生活上の出来事を扱う。ただし、職業や生活状況の影響を受けないという意味ではない。
- 共通生活抽選にも、その時点の職業・勤務地・現在地・活動状況などによる発生確率の補正を認める。必要なら当季節の確率を0%にできる。判定には、先行する定期処理・必須イベント等の解決後の最新状態を使う。
- 0%の場合は当共通枠全体を処理済みのスキップとし、この枠の中立フレーバーへ代替しない。当枠の抽選乱数を消費せず、候補が出るまでの再抽選もしない。
- 抽選を実施する場合も、現在地・勤務地・活動状況などと矛盾するイベントは候補条件で除外する。重みを下げるだけでは済ませず、候補不足を埋める目的でも復活させない。同じ枠のフレーバー候補にも状況条件を適用する。
- 特定の職業に就いたことだけを理由に、共通生活イベントを恒久的に禁止しない。季節ごとに最新の状況から判定し、同じ職業のままでも活動状況等が変われば発生可能になる。
- 第7章の「人生に影響するイベントが出なければフレーバーを判定する」規則は、この状況条件と枠の抑制を満たす範囲で適用する。共通枠を抑制した場合の抜け道にしない。
- 必須・継続予約・職業追加・冬の年末補充は別経路であり、共通枠0%だけでは一括停止しない。ただし、それぞれの候補も現在の状況と矛盾させない。年末補充は既存の条件を維持し、状況に合う中立内容を使う。
- 具体的な補正式・係数・数値は未決。0%を含む状況補正と候補除外の方針の採用であり、数値の仮置きや実装の許可ではない。

### 職業枠・予約・再発管理

職業枠数の入口固定、各枠直前の最新状態による判定、スキップ完了、継続予約の条件再確認と不成立時破棄、クールダウンの数え方を採用した。共通枠の具体的な補正式・係数等は未決。開発用上限の扱いはD08で採用し、具体値はD09の委任方針に従って個別タスクで記録・調整する。

#### 職業イベントの頻度と仕事内容（採用）

- 職業イベントは原則として各季節0〜1件とし、職業ごとの差は主に発生確率と内容で表す。件数不足を補うために同季節の抽選を繰り返したり、枠を追加したりしない。共通生活・継続イベントは別扱い。
- これは仕様書第8.2節の「複数件の季節もあり得る」という幅のある記述を、今回の通常運用として絞った採用判断である。複数件を出す例外は今回採用していない。汎用的に枠数を持つことを理由に、M1で複数件設定・検証を必須にしない。
- 職業・所属組織・雇用形態・等級・経験・技能・活動状況等に応じて、発生頻度だけでなく、仕事の難易度・種類・報酬・危険度の抽選確率も変えられるようにする。既存の勤務地・現在地等による候補条件と合わせ、直前の最新状態で判定する。
- 傭兵専用の分岐に閉じず、職業ごとの設定・候補条件・重み・結果定義で使い分けられる共通の仕組みとする。どの要素を別々に抽選するか、相互の組合せや補正式は未決とし、難易度・報酬・危険度等を無条件に独立抽選するとは決めない。
- 条件に合わない仕事は候補から除外し、候補不足を埋めるために矛盾する仕事を出さない。年ごとの件数を固定・保証せず、年間目安へ届かせるための埋め合わせ抽選も行わない。
- D05の人生イベント優先・フレーバー別系列の規則を維持する。同じ職業枠のフレーバーを含めても原則各季節0〜1件であり、フレーバーの追加・変更で仕事の抽選や報酬結果を変えない。仕事イベント数と職業フレーバー数は区別して集計する。

年間頻度のイメージは次のとおり。固定件数・正式な調整値・必達条件ではなく、試作品で調整するための平均的な目安である。

| 例 | 年間頻度の参考イメージ |
| --- | --- |
| 一般的な職業 | 年1件程度 |
| 個人の傭兵 | 年2件程度 |
| 組織所属の傭兵 | 年3〜4件程度 |

具体的な年間件数・季節確率・補正倍率・報酬額は未確定。所属している期間、活動可能な季節、候補不足、クールダウン等で実際の件数は変わる。上記をそのまま確率の定数へ変換して採用しない。

#### 仕事の遂行方法と単発依頼のテンポ（基本方針を採用）

- 仕事イベントでは、受ける／断るだけでなく遂行方法を選べるようにする。討伐依頼の「慎重に行動する」「正面から突破する」「依頼を断る」は説明例であり、全イベントに同じ選択肢・個数を必須にしない。
- 選んだ方法ごとに、人物の技能・身体能力・装備・依頼難易度等を踏まえて、成功率・負傷リスク・報酬・損失等の結果分布が変わるようにする。単なる文章差し替えにしない。
- 方法の具体的な有利不利、確率式、技能・装備補正、報酬額、条件の組合せは未決。「慎重」が必ず低報酬等の固定関係を、この例だけから決定しない。
- 日常的な単発依頼は、原則として1回の選択から結果判定・報酬や損失の適用まで同じイベント内で完結させる。方法の選択が受諾と遂行の判断を兼ねられるようにし、受諾→出発→戦闘→報酬等へ無条件に細分化しない。
- 重大・特別な依頼は、必要な場合に明示的な複数段階の判断・連鎖を認める。日常依頼まで一律に連鎖化しない。職業枠の原則各季節0〜1件、継続・連鎖の別扱い、D08の上限規則は維持する。
- 戦闘に限定せず、輸送・商業・事務等でも方法選択と結果分布の仕組みを使えるようにする。原作作品の文章・固有内容の流用を許可したという意味ではない。
- 提示だけで結果を抽選せず、有効な選択の解決時に結果を一度確定する。再表示や同じ入力の再送で再抽選・報酬の再適用をしない。D04の再現性とD05のフレーバー非干渉を維持する。
- 今回採用したのは基本方針。具体的な技能・身体能力・装備の状態モデルや補正式は後続で設計する。装備の参照例だけを理由に、M1へ所持品・装備管理や本格戦闘の実装を追加しない。検証用の参照値は採用済みD09の方針と個別タスクの許可範囲で扱う。参照値を置く許可を、新しい状態モデルや補正式の採用と混同しない。

#### 共通する処理規則

- 必須条件と相対重みを別にする。条件に合わない候補は重みが高くても抽選しない。
- 候補順は固定IDのコード単位順にする。配列・ファイル読込順や端末のロケールに依存させない。
- 表示開始時に生涯回数・クールダウン・季節内表示済みIDを一度だけ更新する。同じ待機状態の再表示では更新しない。共通枠と職業枠をまたいでも、同じイベントIDの制限を共有する。
- クールダウンは「発生した季節から次に発生できるまでの最小季節差」とする。値0でも同季節重複は禁止し、最短は次季節。値1も最短は次季節、値2なら間に1季節を置く。春に発生した場合、0／1は夏、2は秋、4は翌年の春から対象に戻る。実際の設定値は別途定める。
- 職業枠数は職業追加段階の入口で確定し、通常は0または1枠として、途中の就職・転職・休職等で増補・再抽選しない。各枠の発生確率・候補・重みはその直前の最新状態で判定する。
- 「枠数／発生確率」と「選択あり候補の重み係数」を別設定にする。係数が実際の表示選択割合と等しいとは扱わず、実件数と分母を別に測る。
- 全候補が不適合・重み0・発生なしでも、その枠は一度処理したものとして進む。候補不足によるスキップ理由は記録する。
- 即時連鎖は追加順のFIFOで処理し、将来の継続予約とは区別する。
- **採用：M1の継続予約は実行季節と実行条件を持ち、実行直前に不成立なら破棄する。自動延期は行わない。** 条件成立までの延期・期限管理が必要な展開は、その内容を決める段階で別途設計する。
- 完済した時点で古い取立て等の予約を無効にし、実行直前にも借金条件を確認する。完済後に新たに借入しても古い予約は復活させず、新しい借入に対応した展開として扱う。
- 同季節の連鎖数と検証プログラムの総処理回数には開発用上限を設ける。連鎖上限は診断停止、検証プログラムの上限は検証中断とし、死亡・寿命・黙ったイベント破棄に変換しない。到達だけで正当な連鎖や長寿を不具合と断定しない。具体値はD09の委任方針に従って個別タスクで記録・調整する。

## 7. 乱数とフレーバー（D04・D05：採用）

### 乱数方式

状態を32bit整数4個で持つxoshiro128** 1.1を採用する。初期化にSplitMix64を使い、著者提供のjumpを使って出生・人生結果・フレーバーの3状態を作る。3系列の状態と消費を独立に管理し、初期化・jump・乱数消費順の再現性をテストする。著者のC実装と説明を参照した設計であり、Terra Lifeでの実装・検証済みではない。

- シードはコア内部では16桁の小文字16進文字列に正規化した64bit値とする。UIで受け付ける入力形式は別途。
- SplitMix64の連続2出力を各「下位32bit→上位32bit」の順で並べ、元となる4ワードを得る。
- 元状態を人生結果用、jump(元状態)をフレーバー用、jumpを2回適用した状態を出生用とする。
- 初期化時の64bit計算にBigIntを使っても、保存する乱数状態はuint32の数値配列だけにする。
- JS移植では32bitの乗算・シフト・回転・符号なし化を明示し、全0の不正状態を拒否する。参照実装から独立に得た固定出力列と比較する。
- u32 / 2^32で0以上1未満の抽選値を作る。確率0／1、候補なし、候補1件は不必要な乱数を消費しない。候補が複数なら固定順の累積重みで1回抽選する。
- 合計重みが非有限になる場合は拒否する。NaN・負の重み・範囲外確率・不正枠数も拒否し、値を黙って補正しない。
- 描画・読出し・診断ログは乱数を消費しない。候補選択と結果分岐の消費順を固定し、ルール版の一部として扱う。

jumpは著者の説明で2^64回の状態遷移に相当する。ここでの「系列を分ける」は状態・消費を分離する意味であり、統計的な独立性の証明を主張しない。

- [xoshiro128** 1.1参照実装](https://prng.di.unimi.it/xoshiro128starstar.c)
- [SplitMix64参照実装](https://prng.di.unimi.it/splitmix64.c)

### フレーバーが人生結果へ干渉しない枠

乱数状態を分けるだけでは、フレーバーが意味のあるイベントの枠を奪ったり、その候補重みを変えたりする場合に非干渉を満たせない。次の優先関係を採用する。第6章の状況補正・0%スキップ・候補除外を前提とする。

1. 各共通／職業枠では、先に「人生の結果に影響するイベント」の発生・候補・重みを人生結果用乱数で決める。
2. その枠で意味のあるイベントが出ない場合にだけ、中立フレーバーの発生と候補をフレーバー用乱数で判定する。共通生活は合計0〜1件を維持する。
3. 意味のある候補が不足した場合も、中立フレーバーから意味のある群へ抽選し直す経路は作らない。
4. 中立フレーバーは人物・関係・ゲーム分岐フラグ・予約・借金等を変更できず、その履歴を就職や死亡等の条件に使えない。
5. 人生イベントとフレーバーでインスタンス番号を分ける。全ログの通し番号やフレーバーの表示数で、後の意味のあるイベントID・抽選を変えない。
6. 出生・死亡を除く当年の記録件数には中立フレーバーも数えるが、それは冬の中立補充にだけ影響する。
7. 成長段階に合う年末補充用の中立定義を検証パックに必ず用意する。通常のフレーバー候補不足はスキップし、年末補充の必須定義欠落はデータ不備として検出する。

この方式では意味のあるイベント側の確率を先に決めるため、全候補を一緒に重み抽選する方式と分布が異なる。具体的な確率・総件数・選択割合は別の調整であり、この案だけで年2〜3件が達成されたとは扱わない。

非干渉検証は、有効なフレーバー設定の文章・重み・発生量を変えた比較で、人物・資金・借金・人生結果用乱数・意味のあるイベントIDと選択結果・死亡が一致することを確認する。全文ログ・全遷移のrevisionの一致は求めない。不正な定義への変更まで同一継続を保証せず、正式な再現保証は同じ全データ版内とする。

## 8. 資金と簡素な経済モデル（D07：基本方針採用、細部に未決あり）

### 資金の意味と名称（採用）

基本ステータスの「資産」を「資金」に変更する。資金は人物が自由に利用できる金銭的な余力であり、不動産・所有物を含む総財産や、借金を差し引いた純財産ではない。借金残高は別管理とする。仕様・UI・内部データ・fixture・説明・診断の名称を統一し、内部の標準名は`funds`とする。命名の具体化であり、財産評価モデルを追加する判断ではない。

### 生活費を定期精算しない（採用、旧案を撤回）

- 毎季の生活費の自動徴収、家庭負担分の定期算定、全額／部分払いの判定、季節ごとの不足額台帳は作らない。
- 家賃・食費等は必要に応じて発生するイベントで扱う。「イベント扱い」を毎季強制発生する生活費徴収へ置き換えない。
- 以前の「定期収入→家庭負担→本人支払」の採用記録は、生活費部分について今回の判断で差し替える。生活費の全額払い・部分払いの比較と、生活費精算より仕事報酬が後になるという旧検証課題は撤回する。旧記録は履歴としてのみ保持する。
- 特定の支出イベントで部分払い・支払延期・未払いの保持等が必要なら、そのイベントの選択と結果として別途確認する。一般の家計管理を先に作らない。

### 3種類の収入方式と反映時点（採用）

| 方式 | 例と収入経路 |
| --- | --- |
| 定期収入型 | 事務職等。季節ごとの資金増加を主な経路とする |
| イベント収入型 | 個人の傭兵等。仕事イベントの結果報酬を主な経路とし、定期収入は0でもよい |
| 混合型 | 組織所属の傭兵等。定期収入と仕事イベントの結果報酬を併用する |

職業・所属組織・雇用形態等に応じ、共通の仕組みで使い分ける。職業名だけで方式を固定しない。第6章の頻度・仕事内容の補正と連携し、傭兵の本格実装をM1へ追加する許可とは区別する。

- 【採用方針】定期収入による資金増加は、日常生活を維持したうえで蓄積できる余剰分として抽象化する。給与総額から生活費を毎季計算する仕組みは不要とする。
- イベント報酬もゲーム用の金額として調整する。日常維持費を別途常時控除して二重計上せず、個別の家賃・食費等のイベント支出との範囲・頻度・金額は抽象化と整合するようにする。
- 定期収入は季節ごとに一度だけ反映する。就職・転職等による定期収入変更は次季節から適用し、当季節分を再計算しない。
- イベント報酬・イベント支出は、その結果を解決した時点で一度だけ反映する。報酬まで次季節へ遅らせず、同じ収入を定期処理とイベントの両方へ計上しない。
- イベント収入型の不足分を埋める定期収入や最低仕事件数は一律に保証しない。頻度・報酬・支出機会・選択肢等を試作品で確認して調整する。

### 経済状況・困窮・明示的な借入（採用）

- 資金が少ないことだけで自動的に借金や生活費不足を発生させない。
- 職業、収入方式と状況、家庭環境、活動状況等も踏まえ、生活困窮イベントや経済的な選択肢の候補条件・重みへ反映する。同じ残高でも生活状況が異なり得る。具体的な閾値・補正式は未決。
- 新規借入は明示的に借入を認めたイベント・選択肢に限る。一般の支出や支払不能から自動借入しない。既存の借金には、別種のイベント効果として利子・延滞等の追加負担を認める。
- 借金に応じた返済要求・取立て等の不利益、完済時の旧予約無効化、実行直前の条件再確認は維持する。困窮と借金を同じ状態にしない。
- P01の基本モデルは、定期収入・イベント収入・イベント支出・明示借入・返済・イベントによる追加負担を扱えることとする。複雑な家計管理・物価計算を要件にしない。

### 借入・返済・追加負担の更新（採用）

| 効果 | 資金の差分 | 借金残高の差分 |
| --- | --- | --- |
| 借入X | ＋X | ＋X |
| 返済X | −X | −X |
| 利子・延滞等の追加負担X | 変更なし | ＋X |

- 借入・返済はそれぞれ資金と借金を同時に一度だけ更新する。片方だけ確定させない。返済額は現在の資金・借金残高のどちらも超えない。
- 指定額を返せない場合は、勝手に減額した返済へ変更しない。「返せるだけ返す」を設けるなら、選択肢として明示する。
- 追加負担は借入・返済と別の効果とし、対象となる借金や延滞等の条件をイベントで明示して、実行直前に再確認する。完済後の古い不利益予約を止める規則は維持する。通常支出からの自動借入として使わない。
- P01では返済要求・取立て・追加負担をイベントで表現できればよい。毎季の利率計算・複利計算・詳細な借金契約システムは必須にしない。利子等の発生条件と増加額は後から調整する。
- 資金・借金の同額更新は、借入または返済の各効果についての規則である。追加負担や別の金銭効果を含むイベント全体に、一律の同額差分を要求しない。各効果と合計を分けて検証する。

### イベント支出の条件（採用）

- 必要額が決まっている任意支出は、資金が足りる場合だけ選択可能とする。解決直前にも条件を確認する。
- 支払いを要求するイベントには、払えない場合の別の選択肢または結果を定義し、進行不能にしない。
- 支払いが成立した額だけ、資金から一度だけ減らす。支払えないのに支払済みにしたり、自動借入したりしない。
- 部分払い・支払延期は、必要なイベントに明示する。システムが支払額を勝手に変更しない。具体的な代替選択・不利益等はイベント内容を決める段階で確認する。定期生活費の不足管理は復活させない。

### 金額と死亡の境界（採用）／資金上限（未決）

- 金額はゲーム用の整数ポイントとし、資金・借金残高はそれぞれ0以上。イベントによる利子・延滞の追加負担も整数額で扱う。具体額は調整値である。
- 精神0・資金0・借金残高だけでは自動死亡しない。健康0とイベント結果で明示された直接死亡は維持する。精神・経済状況から候補や結果確率が変わり、その結果として健康悪化・死亡に至ることはあり得る。
- 資金の上限は未決。「上限なし」を確定事項から外し、「100上限」等もイベントの報酬・支出額と合わせて試作品で検討する。100を正式値・検証用暫定値として採用したわけではない。
- 上限を設ける場合の超過報酬、借入可否、満額反映できないときの扱いも未決。借入の資金だけ切り捨てて借金を全額増やす等の処理を無断で導入しない。借金上限を資金と自動的に共通化しない。上限の有無を使うタスクでは、必要な判断または限定的な検証値の委任を先に確認する。

### 検証方針と残る具体化

## 9. 不正データ・待機・検証上限（D08：主要方針を採用）

### 入力の不受理・診断停止・死亡の3区分（採用）

| 区分 | 例 | 扱い |
| --- | --- | --- |
| 入力の不受理 | 古いイベントへの再選択、選べない行動の指定 | 理由を返し、ゲーム状態・乱数・履歴を変更しない |
| 診断停止 | 不正な確率、参照欠落、計算結果の破綻等 | 最後の正常状態と原因を保持して停止。ゲーム内の死亡として記録しない |
| ゲーム内の死亡 | 健康0、イベントで明示された直接死亡 | 正常な人生の終了として、適用済みの正常な効果とともに記録する |

診断停止時は、原因を特定できるID・季節・処理段階等を保持する。不正データを勝手に補正したり、再抽選・初期化・無関係な既定行動で続行したりしない。

### 部分適用と正常セーブの保護（採用）

- イベント結果や定期処理を一度確定する単位で変更をまとめる。その処理が不正で完了できなければ、途中の効果・乱数更新・履歴を確定せず、直前の正常状態を保持する。
- それ以前に正常に完了・確定した別の処理は取り消さない。例えば「資金を10減らす→不正な効果で失敗」なら、同じ処理内の10の減少も残さない。季節全体を無条件に巻き戻す方式にはしない。
- 正常な結果として死亡した場合は、不正による失敗とは区別し、死亡に至るまでの正常な効果を保持して確定する。
- 診断停止中の不正状態で正常なセーブデータを上書きしない。診断情報を保存する場合も、再開用の正常セーブとは分ける。
- M1では外部I/Oを持たず、最後の正常状態と停止原因を保持できる契約を扱う。M3で保存処理に接続するとき、不正状態の書込みで正常セーブを上書きしないことを検証する。診断情報を別途保存する機能の必須化や、保存方式・移行・復旧UIの採用ではない。

### 開発用上限と検証中断（採用、具体値は未決）

- 同季節の連鎖処理には開発用の回数上限を設ける。超過時は最後の正常状態と原因を保持して診断停止する。
- 一生を自動生成する検証プログラムにも総処理回数の上限を設ける。到達時は検証中断として扱い、キャラクターの死亡や寿命として記録しない。検証プログラムの中断をゲーム内の終了状態へ変換しない。
- 上限到達は停止理由として明示するが、それだけで正常な長寿や正当な連鎖を不具合と断定しない。設定値と実際の検証結果を見て調整する。
- 残るイベントを黙って捨てたり、強制死亡させたりして上限を回避しない。選択待ちや通常の中断は、停止不能と区別する。
- 具体的な上限値は、D09の採用済み数値委任方針に従い、各タスクの範囲内でAIが仮設定できる。値・用途・理由・見直し条件を記録し、検証結果を見て調整する。コード実装の許可はタスクの範囲とともに別途確認する。

### データ検証の具体化候補

イベントID重複、参照切れ、不正な確率・重み・枠数、全選択不可、無効な既定行動、フレーバーへのゲーム効果混入等を検証する。入力や実行時にも、選択可否・予約条件・支出・返済・追加負担の条件を確認する。具体的な検証配置・型構造は採用した契約を満たすよう実装タスクで定める。

M3の保存データ検証・移行・復旧UIは未設計。M1の診断状態をそのまま正式保存形式とみなさない。

## 10. 検証用データと受入条件（D09：数値委任方針を採用、受入範囲は個別確認）

### データの扱いと数値委任（採用）

正式な生活イベント集とは別に、fixtureであることが分かるID・説明・調整区分を付ける。検証用の職業は枠数・選択係数の差を試す識別子でよく、架空の原作職業設定を追加しない。

各タスクで対象を限定し、次の検証用数値は、その範囲内でAIが仮設定できる。個々の数値の逐次確認は不要とする。

| 委任する数値 | 検証での用途 |
| --- | --- |
| 検証用の初期値・出生抽選の重み | 出生固定・再抽選・再現性、必要な初期状態を試す |
| 抽選確率・重み・効果量・クールダウン | 成功・失敗・死亡等の分岐や再発境界を試す |
| 収入・報酬・支出・借入・返済・追加負担の額 | 資金・借金の更新と支払境界を試す |
| 診断停止の連鎖上限・検証中断の総処理上限 | 停止の区別と正常状態の保持を試す |

- 設定した値・用途・選定理由・見直し条件を記録し、正式なゲームバランスへ自動昇格させない。原作確認済みの数値や正式コンテンツとして扱わない。
- 成功・失敗・死亡等の重要分岐は、採用済み仕様の範囲内で固定シナリオ・固定入力・境界値等を使い、確実に検証できるようにする。少数回の偶然の抽選だけで分岐を確認済みにしない。
- 検証を通す目的で採用済み仕様・期待結果を変更しない。検証上限を通常の寿命へ変換したり、幼少期死亡を防ぐ保護を付けたりしない。
- 資金上限の有無・100上限・超過時の扱い、仕事の新しい確率計算式・技能補正・装備の状態モデル等、ゲーム挙動・設計に関わる未決事項は委任に含めない。必要な時点でユーザーへ確認する。
- 委任は各タスクに限定する。D09の承認だけで、全機能の実装・依存導入・全検証候補の一括実行を許可したとは扱わない。

死亡する固定シナリオで「出生から死亡まで」を確認する一方、実行上限で止めたシナリオは検証中断と報告する。全シードが必ず一定年齢で死亡する仕組みや、幼少期死亡を防ぐ保護は追加しない。長寿分布や文章の面白さはM1の達成条件にしない。
