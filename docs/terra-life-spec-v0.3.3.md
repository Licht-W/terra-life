## 1. 目的とゲームの方針【確定】

アークナイツの舞台「テラ」に生まれた一般住民として、出生から死亡までの人生を体験する、確率中心の人生シミュレーターである。

- 原作の社会・文化・国家・種族・源石・天災・鉱石病などの世界観を尊重する。
- 原作の主要ストーリー、事件、登場人物を詳細に追体験することは目的としない。
- 人生を総合スコアで成功・失敗に分類しない。選択と出来事の記録自体を成果物とする。
- 単純な能力値育成や、戦闘力ランキングを中心にしない。
- 原作で確認できない人口分布・寿命・発生率などは、ゲーム用の調整値として明示する。
- 設定の空白を埋めるためだけに、断定的な独自設定を増やさない。
- Project Moon Lifeは形式や操作の参考とし、イベント文章・独自設定は流用しない。

## 2. 基本のプレイ体験【確定】

1. 出生条件をランダムに決定し、必要なら開始前に再抽選する。
2. 開始後は年齢と季節が自動進行し、出来事が表示・記録される。
3. 時限式・停止式のイベントで行動を選択する。通常進行中は手動の一時停止・再開ができるが、時限式の解決中は他のゲーム内操作を禁止する。
4. 年齢、職業、居住地、状態、過去の選択によって出来事が変わる。
5. 死亡した時点で進行を終了し、人生記録を閲覧できる。

人生記録は、`── 12歳 ──`の年齢見出し、`[秋] 本文`、必要に応じて`▸ 選んだ行動`と結果文を表示する。一件は原則1〜3文とし、重大イベントのみ長文を許容する。親の具体的な職種など、人生に関係しない出生情報は必須にしない。

【提案】一度開始した人生の出生条件は固定する。再抽選は開始前だけにし、新しい人生は別の記録として扱う。P01は「進行中1件＋直前に完了した人生1件」の保存でよく、無制限のアーカイブは対象外とする。

| 基本5ステータス、簡素な収支、明示的な借入・返済と未返済の不利益イベント | 高度な経済・市場・家系シミュレーション、詳細な借金契約管理 |

【提案】鉱石病はP01では感染・進行のゲーム処理を実装しない。世界観の文章として触れる場合も、未実装の感染判定や治療機能があるように見せない。

【提案】完了時のコンテンツ目安は、独立したイベント定義40件以上、うち選択あり12件以上、継続する流れ3組以上とする。出生・死亡・単なる同義文の差し替えは40件に数えない。これは制作量の仮目安であり、職業別の追加抽選によって総件数が増え得ることを踏まえ、年間件数・反復率・職業差の試遊結果を優先する。最初の工程では少数の検証用データでよい。

## 4. 時間・一時停止・選択

### 4.1 ゲーム内時間【確定／提案】

- 【確定】1年を春・夏・秋・冬に分け、季節ごとにイベントの発生を判定する。
- 【提案】0歳の春から開始し、冬の完了後に年齢を1増やす。誕生日の日付は持たない。
- 【提案】経過季節数を整数で保持し、年齢・季節はそこから一貫して求める。
- 【調整値】季節間の表示待ち時間、速度倍率、時限式の制限時間。設定箇所を一つにまとめる。
- 【提案】倍速は通常の表示待ち時間だけを変え、選択の制限秒数には影響させない。
- 【確定】P01では年齢と季節だけをゲーム内年代の基準とする。テラ歴・具体的な暦年・原作史実の年表には接続しない。

### 4.2 選択方式【確定】

| 方式 | 動作 |
| --- | --- |
| 選択なし | 出来事と結果を記録し、効果を適用する |
| 時限式 | 最前面のモーダルで制限内に選ぶ。期限切れなら既定行動を実行する。提示中の手動停止・他のゲーム操作は不可（非表示・復帰時の例外は4.4） |
| 停止式 | 自動進行を止め、プレイヤーが選ぶまで先に進まない |

重大な進路・就職などは停止式を中心とし、小さな日常的選択も用意する。

### 4.3 時限式の処理【確定／実装細部は提案】

【確定】P01では同時に未解決の選択イベントを1件だけ扱う。時限式の選択待機中は**制限時間のみ**進み、次の季節への遷移・定期収支・追加抽選は解決まで待つ。時間切れ時はそのイベントに定義した既定行動を選ぶ。

【確定】時限式イベントは画面最前面の**操作を遮断するモーダル**で提示する。表示中は他のゲーム内UI、手動一時停止、速度変更、記録の操作、通常の画面遷移を無効化する。選択するか時間切れになると一度だけ解決する。モーダルを背景クリックやEscで閉じて期限を回避できないようにする。

【提案】時限式が始まる時点で通常の手動停止中であることはない（停止中は新規抽選しない）。手動停止の受付はモーダル表示の前に締め切り、入力の競合を一意に解決する。表示完了とタイマー開始の起点を定義し、画面描画や処理負荷で不公平な短縮が起きないようにする。

【注意】タブ非表示時・復帰待ちの時間停止は別途採用済みの例外である。これを使うとプレイヤーが現実時間をかけて考えられる点は許容し、P01ではアンチポーズ対策や背後時計の導入は行わない。

### 4.4 停止と復帰【基本動作は確定／競合処理は提案】

- 【確定】通常進行中には手動停止・再開ができる。ただし時限式モーダル表示中の手動停止は受け付けない。
- 【確定】タブ非表示中とブラウザを閉じている間は、季節進行も時限式の残り期限も減らない。経過分のまとめ処理は行わない。
- 【確定】非表示から戻った時とセーブ読込後は停止状態で表示し、明示的に再開する。
- 【提案】手動停止・非表示・復帰待ち・停止式選択待ち・死亡を独立した停止理由として管理する。一つを解消しても別の停止理由があれば進めない。
- 【補足提案】季節進行の可否、制限時間の進行可否、操作の可否を分ける。時限式の選択待ち自体は季節と通常操作を止めるが、制限時間を止める理由にはしない。非表示・復帰待ちでは制限時間も止める。
- 【提案】復帰待ち中の通常ゲーム操作・イベント選択は無効とするが、**明示的な「再開」操作だけはシステム復帰用として例外的に許可**する。時限式モーダルの上に復帰案内を表示する等、他の画面操作を解放せずに再開可能なUIとする。再開後は同じイベント・残り時間から判断を続ける。
- 【提案】通常の手動停止中の新しいイベント発生はない。停止式イベントが表示された場合は、時間制限なしで行動を選べる。停止式の解決後はほかに停止理由がなければ進行を再開する。
- 【提案】時限式の期限到達とクリックの競合は一つの規則で確定し、適用・乱数消費・記録の二重発生を防ぐ。境界では期限到達を優先する案を継続する。

## 5. ステータスと人物状態

### 5.1 基本ステータス【項目確定】

| 項目 | 用途 | 数値の扱い |
| --- | --- | --- |
| 健康 | 疾患・負傷・回復・身体状態 | 暫定0〜100 |
| 精神 | ストレス・心理的な安定 | 暫定0〜100 |
| 資金 | 人物が自由に利用できる金銭的な余力。教育・治療等のイベント支出に用いる。総財産や不動産・所有物の評価額ではない | ゲーム用の資金ポイント、固定上限なし。未返済の借金は別管理 |
| 知識 | 一般教育と学習の蓄積 | 暫定0〜100 |
| 人脈 | 社会的なつながり・支援へのアクセス | 暫定0〜100 |

- 【確定】基本値は数値表示し、専門技能は原則として文章・段階評価で表示する。
- 毎季すべてを増減させる必要はない。自然変動、出来事、状態に応じた確率補正を組み合わせる。
- 値同士を無条件に直結させず、生活条件・出来事・選択を介して影響させる。
- 個別の家族・友人関係は、人脈の総量とは別に保存する。
- 【確定】金銭の基本ステータスは、仕様・画面・説明・内部データで「資金」に統一する。内部の標準名は`funds`とする。総財産や不動産の管理を、この名称変更のために追加しない。

### 5.2 資金・収入・イベント支出【基本モデル確定／具体的な数値・支払条件は提案・調整】

- 【確定】P01は、定期収入、イベント収入、イベント支出、明示的な借入・返済を扱う簡素な経済モデルとする。複雑な家計簿・物価計算・所有物評価は必須にしない。
- 【確定】**毎季の生活費は自動徴収しない。** 家賃・食費等は必要に応じて発生するイベントで扱う。定期生活費の全額払い・部分払い・不足額台帳や、そのための家庭負担額の季節精算は作らない。イベントで扱うことを、毎季必ず生活費イベントを出す仕組みへ置き換えない。
- 【確定】職業・所属組織・雇用形態等により、定期収入型・イベント収入型・混合型を使い分ける。事務職、個人の傭兵、組織所属の傭兵はそれぞれの説明例であり、職業名だけで方式を固定しない。
- 【採用方針】定期収入による資金増加は、日常生活を維持したうえで蓄積できる余剰分として抽象化する。給与総額と生活費の内訳を毎季計算する必要はない。イベント報酬もゲーム用金額として調整し、日常維持費を二重計上しない。個別に定義した家賃・食費等の支出イベントとの範囲・頻度・金額は、この抽象化と整合するように調整する。
- 【確定】イベント収入型では、仕事イベントの結果による報酬を主な収入源にでき、定期収入は0でもよい。収入不足を埋めるための定期収入や最低仕事件数を一律に保証しない。
- 【確定】定期収入による資金増加は季節ごとに一度だけ反映する。就職・転職等による変更は次季節から適用し、反映済みの当季節分を遡って再計算しない。仕事報酬・臨時金・イベント支出は当該結果の解決時に一度だけ反映し、定期収入と二重計上しない。
- 【確定】資金が少ないことだけで自動的に借金や定期生活費不足を発生させない。職業、収入の方式・状況、家庭環境、活動状況等を踏まえ、生活困窮や経済的選択肢の候補条件・重みに反映する。残高が同じでも生活状況は異なり得る。具体的な判定式や閾値は未決。
- 【確定】**借金は、明示的に借入を認めた一部のイベント・選択肢でのみ発生する。** 一般の支出・治療費・進学費用を自動借入へ変換しない。資金と未返済の借金は別管理とする。
- 【確定】借金がある場合は返済要求・取立て等の不利益イベントが発生し得る。借金の有無・規模・経過等を使い、発生条件を定義できるようにする。
- 【提案】金額はゲーム用の整数ポイントに統一し、資金・借金残高はそれぞれ0以上とする。実際の貨幣価値は断定しない。上限なしを、非有限値や数値精度の破綻を許す意味にはしない。
- 【提案】一般の支出イベントは必要額を満たすか確認し、足りなければ未成立・別の選択肢等、そのイベントで明示した経路を使う。支払えないのに支払済みにしたり、自動借入したりしない。部分払い・未払いの保持・後の入金での再支払等は、必要なイベントの設計時に確認し、全イベント共通の家計管理として先行導入しない。
- 【提案】扶養・家庭環境は出生条件、困窮判定、イベント候補・支援の選択肢等で扱う。乳幼児に成人向けの収入・支出・借入をそのまま適用しない。毎季の生活費負担表は必須にしない。
- 【補足提案】借入額と増やす資金、返済額と減らす資金・借金は、ひとまとまりで一度だけ更新する。返済額は現在の資金・借金の両方を超えない。借入履歴等は実際に使う最小情報に限定する。
- 【確定】継続予約は実行直前にも条件を再確認し、不成立なら破棄して自動延期しない。完済後は古い取立て等の予約を無効にし、再借入でも復活させない。新たな借入は新たな展開として扱う。
- 【提案】P01では詳細な借入契約、自動返済、利息、破産を作り込まない。返済は明示的なイベント／効果で扱う。具体的な返済可否・金額指定等は必要なイベントに応じて定める。
- 【調整値・検証】定期収入の余剰額、仕事の報酬・費用、家賃・食費・学費・治療費等のイベント支出、支援額、借金関連条件・重み、困窮条件を試作品で調整する。仕事頻度と資金推移、支出機会、選べる行動、困窮イベントの発生を併せて確認する。生活費の定期徴収額・自動不足額は調整対象として新設しない。

### 5.3 裏能力・背景【構造採用／詳細保留】

- 出生時の素質：身体的素質、学習適性、アーツ適性など。
- 後天的能力：身体能力、職業技能、専門知識など。
- 背景・状態：種族、出身国、居住地、家庭の経済状態、学歴、職業、職種、役職、勤務地、所属、個別関係、負傷・疾患、履歴フラグ。
- 裏能力の値は原則非公開とし、適性検査や実績によって「優れている」「未判定」等の情報を開示できる。
- アーツ適性、実際の技能、本人の認知は別概念とする。ただしP01で将来用の空の仕組みを作り込まない。
- 将来も単一の公開戦闘力に集約しない。適性・訓練・装備・環境・運などで判定する。

## 6. 成長・老化・死亡

- 【確定】実年齢、成長段階、身体の老化度、種族特性を分離する。
- 【確定】全種族に同じ成人年齢・老年期・寿命を適用しない。不確かな原作設定を確定情報として書かない。
- 【採用方針】P01ではフェリーン用の仮成長・老化パラメータを用意し、後から差し替え可能にする。
- 【確定】幼少期を含め、事故・病気等で死亡し得る。最低生存年齢の保護は置かない。
- 【確定】死亡は季節処理やイベント結果で起こり、健康0以外の死亡原因も認める。
- 【確定】健康0を死亡条件の一つとし、事故等の直接死亡も認める。【提案】精神0や借金だけでは自動死亡させない。
- 【提案】死亡を確定した時点で、季節の残り処理・連鎖・年末補充・次季節への遷移を打ち切る。死亡記録は一度だけ残し、操作や古いタイマーで再開できないようにする。
- 【提案】死亡がイベント結果の場合は、その出来事・選択・結果の記録と死亡情報を対応づけ、重複した死亡通知を並べない。
- 【保留】鉱石病拡張時は、感染、病状進行、曝露、治療、社会的認知を分離する。感染をアーツ才能の自動獲得にしない。

【提案】開発用の長時間実行上限を設けても、それを通常プレイの寿命や死亡として記録しない。上限到達は検証中断として報告し、長期生存の分布や老化処理を調べる。

## 7. イベントの属性【v0.1の意図を維持した整理案】

「生活上の重要さ」「発生経路」「選択方式」を分ける。v0.1の強制・継続は削除せず、組み合わせられる属性として表現する。

| 軸 | 値の例 | 意味 |
| --- | --- | --- |
| 内容分類 | フレーバー／通常／重要 | 描写のみか、小さな変化か、大きな転機か |
| 発生経路 | 通常抽選／条件成立／継続予約 | どの仕組みで候補になるか |
| 強制変化 | あり／なし | 選択で回避できない変化を含むか |
| 選択方式 | なし／時限式／停止式 | プレイヤーがどう関与するか |

例えば就職は「重要＋条件成立＋停止式」、過去の交流の続きは「通常＋継続予約＋時限式」、事故は「通常または重要＋通常抽選＋強制変化＋選択なし」と表せる。強制変化の後に対処を選ぶイベントも、必要になれば表現できる。

### 7.1 イベントデータの契約【提案】

| 項目 | 内容 |
| --- | --- |
| 固定ID・改訂番号 | 文章変更後も識別できるIDと、定義の改訂番号 |
| 内容・発生属性 | 上記の分類と、対象の季節・年齢段階など |
| 抽選枠の対象 | 共通生活／職業追加の対象区分。両方の候補になれる場合も同一季節の重複発生を管理する |
| 発生条件 | 生存、居住地、職業、状態、履歴等の条件。必須条件と重み補正を混同しない |
| 抽選重み | 通常抽選に使う相対値。重み10は10％を意味しない |
| 選択定義 | 固定選択肢ID、本文、選べる条件、方式、時限式の期限と既定選択肢 |
| 結果定義 | 結果文、確率分岐、ステータス・技能・資金・職業・関係・状態への効果。明示的な借入・返済と後続の不利益イベントも表せるようにする |
| 再発制限 | 生涯上限、クールダウン、同一季節の重複禁止など |
| 継続予約 | 次イベントID、実行季節、期限、条件が崩れた場合の破棄方法 |
| 支出・借金条件 | 資金不足時の扱い、明示借入の可否、返済・不利益の発生条件。詳細な契約を必須にしない |
| 出典・調整区分 | 原作記述に基づく部分、ゲーム用仮定、確認待ち事項 |

条件・効果は型で表せるデータにし、任意コード文字列の評価で実行しない。イベントごとに専用のプログラムを増やし続ける構成も避ける。P01で必要な条件演算・効果から始める。

【提案】選択方式が時限式または停止式のイベントについては、表示前に選択可能な行動が最低1件あることを検証する。時限式の既定行動は必ず選択可能なものを用意する。表示後の文面・選択肢・結果定義は、その発生インスタンスに固定する。参照切れ等で進行不能になった場合は診断付きで停止し、無関係な行動を自動選択しない。

### 7.2 フレーバーと選択の意味【確定／補足提案】

- フレーバーは原則選択なしで、ステータス、状態、関係、物語の分岐フラグに効果を持たない。
- 【提案】表示済み履歴、再発制限、記録件数、抽選状態など、表示と運用に必要な内部情報の更新は認める。したがって「ゲーム状態の全バイトが不変」という意味ではない。
- 【提案】フレーバーの閲覧自体を、就職・死亡等の条件や有利不利の原因にしない。フレーバーの出現抽選・文章差し替えに使う乱数系列は、人生の結果判定に使う乱数系列と分ける。
- 選択肢を設けるなら、基本的に選択に応じた何らかの状態変化を用意する。数値増減だけでなく、技能・関係・進路・履歴フラグでもよい。
- 【提案】確率によって同じ結果になる場合は許すが、選択肢間で結果分布も将来の影響も完全に同一なら、選択にする必要を見直す。
- 表示だけの微差を、意味のある選択の代わりにしない。

## 8. 発生頻度と職業差

### 8.1 頻度【方針は確定／具体的な回数は調整値】

- 【確定】一般的な生活では年2〜3件程度の記録を出発点の目安にするが、**職業・職種・活動状況によって年間件数そのものが増減してよい**。一律の年間上限は設けない。
- 【確定】各季節にイベント発生を判定する。共通の生活抽選は原則0〜1件とし、職業に応じた追加抽選や、連鎖・必要な転機によって同じ季節に複数件起きてもよい。
- 【確定】生存した各年に最低1件の記録を目標とし、冬まで0件なら条件に合うフレーバーで補う。死亡年は死亡記録を必ず残す。
- 【確定】使用上限、クールダウン、年齢別表現で短期間の同文反復を避ける。

【提案】2〜3件は一般的な人物の複数人生における基準で、職業の忙しさを押し戻すための強制枠ではない。出生・死亡記録は通常件数と分けて集計し、年末補充用の中立的なフレーバーを用意する。追加イベントが多い職業では履歴の反復と読書負担も測定する。

### 8.2 抽選方式【複数抽選枠を採用／具体的な計算は提案】

各季節の発生処理では、以下の役割の異なる枠を使う。前の結果が後の状態・候補に影響するため、抽選結果同士が統計的に独立であることを意味しない。

1. **条件成立・継続予約**：進路の転機や過去イベントからの継続など、優先すべき候補を処理する。
2. **共通の生活イベント抽選**：原則として季節0〜1件。職業・勤務地・現在地・活動状況等による確率補正と0%を認め、矛盾する候補はフレーバーを含めて除外する。0%では当枠のフレーバーへ代替せずスキップする。特定職業だけを理由とした恒久禁止はしない。
3. **職業イベント追加抽選**：原則各季節0〜1件。職業・所属・雇用・等級・経験・技能・勤務地・活動状況等で発生確率と候補を変える。共通生活・継続イベントは別に扱い、固定の年間件数を保証する埋め合わせ抽選は行わない。
4. **イベントの連鎖・特別な発生**：各イベントの結果から予約・連鎖を処理する。最新の状態で条件を再確認する。
5. **空白年の補充**：冬の終了時にその年の生存中の記録がなければ、中立的なフレーバーを記録する。

【提案】各抽選枠では「その枠の抽選を実施する確率」と「候補イベント間の相対重み」を分ける。発生条件・再発制限を満たす候補を抽出し、合計重みが正なら抽選する。候補不足時は無理に無関係なイベントを出さず、診断に残す。共通抽選と職業抽選で同じイベントを二重に選ばない識別規則を持つ。

【採用方針】職業の忙しさは、原則各季節0〜1件の範囲で主に発生確率・内容に反映する。通常の枠数は0または1とし、複数件を出す例外は今回採用しない。選択の多さは選択あり／なし候補群の割合または重み係数で別に調整する。【補足提案】両者を別パラメータにし、単に枠を増やして選択割合も調整したことにはしない。割合と群内の相対重みを使う場合は、群を選んでからその中で重み抽選する等、実装方式と乱数消費順を決定記録に残す。

【補足提案】発生確率・割合は0〜1、相対重みは0以上の有限値、枠数は0以上の整数に限定する。不正値は検証で拒否し、重み0は選ばない。候補群が空の場合のスキップ等も一意に定め、候補不足と設定値の効果を区別して集計する。

【提案】必須候補の順番は明示した優先度、同値なら固定ID順にする。継続予約については第5.2節の採用判断を優先し、実行直前の条件不成立時は破棄して自動延期しない。追加抽選は1枠ずつ解決し、前の結果が後の条件・重みに反映される。1季節に複数件あっても処理段階・乱数消費・セーブ再開は再現可能とする。

【補足提案】共通・職業枠を通じ、その季節に表示開始したイベントIDを管理し、同じ定義を重ねて表示しない。抽選スキップも枠の処理完了として保存し、読込後に再挑戦しない。

【補足提案】職業追加段階に入った時点の職業・活動状態で、その季節の追加枠数を一度決める。各枠の直前に最新状態で発生確率・候補・重みを再判定するが、就職・転職・復職等で枠数を補充・再抽選し直さない。失業等で候補が消えれば残り枠をスキップする。この枠数固定案は循環・無制限追加を防ぐ実装案であり、職業差そのものの確定条件とは区別する。

### 8.3 職業差【確定】

職業・職種・役職・勤務地・繁忙度により、①**職業イベントが発生する総頻度**、②**選択イベントの割合・重み**、③**危険イベントの頻度・内容**をそれぞれ変える。日常的な判断が少ない事務職では選択・職業イベントが少なめ、移動や判断の多い職では多めとなり得る。仕事と無関係な生活・フレーバーまで不自然に消さない。

所属組織・等級・経験・技能・活動状況等は、発生頻度だけでなく仕事の難易度・種類・報酬・危険度の抽選確率にも反映できる共通設計とする。傭兵専用の処理にはしない。一般職で年1件程度、個人傭兵で年2件程度、組織所属傭兵で年3〜4件程度は、固定件数ではない平均的な参考であり、具体確率・補正倍率・金額は未確定とする。

同じ職業でも休職・閑散期・勤務地などによって頻度は変化し得る。選択イベント数が多い職業に一方的な成長利益を与えず、定期成長・時間・費用・失敗・危険との釣り合いを取る。P01では事務・工場・商業の間で差を検証し、トランスポーターや競技騎士は将来例に留める。具体的な職業別倍率や季節抽選回数は試遊で調整する。

## 9. 季節処理の契約【具体的な順序は提案】

季節は、次の処理を完了してから次へ進む。定期処理・抽選・結果適用を、タイマーの再実行だけで二重に行わない。

1. **開始**：生存と処理段階を確認する。年齢・成長段階・生活条件を整える。
2. **定期処理**：定期収入による資金増加、継続状態、健康・教育・技能・老化等の定期変化を一度適用する。生活費の定期徴収や不足額精算は行わない。
3. **死亡確認**：死亡が成立したら記録して終了する。
4. **必須・予約処理**：条件成立イベントと継続予約を順番に処理する。各イベント直前に条件を再確認する。
5. **共通生活抽選**：その時点の状態で通常0〜1件を抽選する。
6. **職業追加抽選**：原則各季節0〜1件の範囲で、職業・所属・活動状況等に応じた確率・候補・重みで判定する。直前の最新状態を参照する。
7. **イベント解決**：選択待ちならその場で中断する。選択または期限切れで結果を確定し、効果・履歴・予約を一度だけ適用する。死亡なら以降を打ち切る。
8. **連鎖確認**：発生した連鎖を最新状態で処理し、解決後に元の抽選処理へ戻る。すでに処理済みの枠を再抽選しない。
9. **季節完了**：冬なら空白年の補充を行う。生存していれば経過季節数を1増やす。

4〜6のどの枠で表示されるイベントも、7〜8の解決処理を共通で使う。イベント発生、表示開始、結果確定は別の段階とし、各抽選枠の実施済み情報と途中位置を保存・再開できる。

【補足提案】上の番号は、全抽選を先に済ませてからまとめて解決する順序ではない。各必須・共通・職業枠から7〜8へ進み、そのイベントと連鎖を解決してから、未処理の次候補・次枠へ戻る。死亡時は戻らず終了する。季節の途中の選択は、後続の抽選直前に反映する。

【補足提案】条件成立イベントは、一度限りの成立記録や再発制限を持たせ、条件が真であるだけで同じ季節に繰り返さない。連鎖は明示的な追加キューで管理し、元の必須候補全件を無条件に再走査しない。

【補足提案】職業・収入・家庭環境等から成立する困窮候補や、借金の不利益候補は、必須・予約・共通生活等の対応する経路で扱う。定期的な生活費不足を生成する処理は設けず、困窮と明示的な借入を区別する。強制発生か確率抽選かはイベント定義で明示し、同季節の新規成立や即時連鎖はM1の採用判断に従う。

【提案】同じ季節の連鎖数には開発用の上限を持たせる。超過時は診断付きで進行を止め、黙ってイベントを捨てたり死亡させたりしない。

職業・状態が変われば、その後の同季節の条件判定と次季節の処理に反映する。反映済みの定期収入による資金増加だけは遡って再計算しない。

## 10. 状態・再現性・セーブ

### 10.1 実装を分ける単位【提案】

| 単位 | 責務 |
| --- | --- |
| シミュレーションコア | 時間、人物状態、抽選、条件・効果、死亡、イベント待機・解決 |
| コンテンツ | イベント文章・条件・効果、職業定義、成長・経済等の調整値 |
| アプリ制御 | 表示待ち・選択期限の時計、停止理由、入力、保存呼出し |
| 保存 | 保存データの検証、読込、版の照合、書込失敗の通知 |
| UI | 状態・人生記録・選択肢の表示、ユーザー操作の受付 |

【採用方針】コアは画面から独立した純粋なTypeScript関数を中心にする。コアからReact、DOM、実時計、ブラウザ保存APIへ直接依存しない。

最小状態には、人物、経過季節数、季節の処理段階、処理済み抽選枠と残り枠、生死、乱数状態、未解決イベント、適用済み履歴、クールダウン、継続予約、人生記録、選択記録を含める。単一の`isPaused`だけで、死亡・選択待ち・手動停止を兼用しない。

【補足提案】残りの必須候補・連鎖キュー、解決後の戻り先、季節内の表示済みID、借金・困窮条件に必要な最小情報も状態に持つ。結果の確率抽選は解決時に一度だけ行い、表示開始や読込だけで抽選し直さない。

### 10.2 再現性【採用方針／具体化は提案】

同じ初期条件、シード、選択記録、ルール・イベント・調整値の版で、同じゲーム内結果を再現する。

- 出生の再抽選と開始後の乱数を区別する。開始した人生の出生条件と、開始時の乱数状態を保存する。
- 候補の並び順、同優先度の順番、乱数アルゴリズムを固定する。実時計・描画回数・表示速度で抽選結果を変えない。
- シードだけでなく、途中再開に必要な乱数状態も保存する。
- 選択記録にはイベントの発生インスタンスID、選択肢ID、選択方法（手動／期限切れ）を残す。実時間の全クリック履歴は不要とする。
- 手動か期限切れかで結果を変えるなら、その区別もリプレイ入力として使用する。
- 出生、人生の結果判定、フレーバーの出現抽選・文章差し替えで乱数系列を分ける。フレーバー側の乱数消費によって、後の人生結果（死亡判定等）が変化しないようにする。診断ログの出力自体は乱数を消費しない。
- データ版には調整値も含める。版が変わった人生の同一結果までは保証しない。

「同じシード」は、再抽選履歴・データ版・選択入力を省いても同じになるという意味ではない。

### 10.3 セーブ・復帰【採用方針／具体化は提案】

- ブラウザに自動保存し、進行中の再開と死亡後の記録閲覧を可能にする。
- 保存には形式版、ルール版、コンテンツ・調整値版、コア状態、選択記録、必要な表示待ち残量を含める。コア状態には抽選枠の予算・処理位置・完了情報、残りキューと戻り先、季節内表示済みID、必要な借金・困窮情報も含める。
- 結果適用後の状態・乱数状態・履歴は、途中だけが残らないよう同一の保存単位にまとめる。
- 出生確定、イベント待機開始、結果確定、季節完了、停止、死亡を保存の区切りにする。
- 時限式は残りの有効時間を保持し、待機開始・定期保存・タブ非表示・復帰待ち開始の保存時に残量を固定する。ブラウザ終了直前の保存成功は前提にせず、強制終了では直近の成功保存時点へ戻ることを許容する。通常の保存間隔は調整値とし、手動停止で時限式の期限を止める経路は設けない。
- 読込時は未解決イベントと残り時間を復元する。収支や効果を再適用しない。
- 時限式の読込後も同じモーダルと操作制限を復元し、明示再開後に残り時間から続行する。制限時間を初期値へ戻さない。
- データ破損・非対応版では、黙って初期化せず再開できない理由を表示する。P01では移行処理を必須にしない。
- 書込失敗時は画面で通知する。保存済みであるかのように表示しない。
- 保存方式は実装時に選ぶ。P01のデータ量で十分なら簡素な方式を使い、不要なバックエンドを追加しない。

【提案】P01は同時に1タブでの操作を対象とする。同じ保存先を複数タブで開いた場合は重複を検知して後の進行を止め、互いの状態を上書きしない。複数端末の同期や完全な共同編集制御は対象外とする。

### 10.4 検証ログ【提案】

開発用ログには季節、処理段階、候補IDと重み、選ばれたID、乱数状態または抽選値、選択元、効果差分、死亡原因、版情報を記録できるようにする。裏適性や内部確率を通常のプレイ画面へ常時露出させない。

## 11. 最小UI【提案】

| 画面 | 必要なもの |
| --- | --- |
| 出生 | 出生条件、再抽選、開始、再現用シードの確認・指定 |
| 人生進行 | 年齢・季節、生存状態、基本5値、職業・主な状態、人生記録、停止・再開・速度 |
| 選択表示 | 出来事、選択肢、時限式の残り時間と既定行動、停止式であることの表示。時限式は背景操作不可のモーダルとする |
| 人生終了 | 死亡時年齢・季節・原因、出生からの記録、次の人生を始める操作 |
| 復帰・保存エラー | 再開、保存状況、版不一致や保存失敗の説明 |

人生記録は追記型にする。過去ログを読んでいる間の強制スクロールを避け、最新記録へ戻れるようにする。選択肢はキーボードでも操作できるようにする。ビジュアルや名称の最終決定は別途行い、P01では読みやすさを優先する。

【確定】時限式イベント中はモーダルの外側への入力（背景クリック、画面遷移、手動一時停止、速度変更等）を受け付けない。【提案】フォーカスをモーダルに閉じ込め、選択と期限切れを明瞭に表示する。タブ非表示からの復帰時とセーブ読込後は、モーダル上の復帰案内等の**システム再開操作**を認め、他のゲーム操作を解放しない。背景のボタンを無効表示にするだけでなく、アプリ制御側でも禁止入力を拒否する。

【確定】金銭ステータスの表示名は「資金」とする。不動産等を含む総財産や、借金との差引純資産の表示として扱わない。内部値は`funds`、借金は別情報とし、同じ意味の旧名フィールドと二重管理しない。

## 12. 技術・リポジトリ構成【提案】

v0.1の候補を具体化し、React + TypeScript + Viteを第一案とする。コア・データ検証にはVitest等、ブラウザ操作の主要経路にはPlaywright等を用いる。実際の依存版は着手時に確認し、ロックファイルで固定する。

構成の目安は次のとおり。工程や責務が明確なら、細かなファイル名・関数名まで一致させる必要はない。

| 配置例 | 内容 |
| --- | --- |
| `src/domain/` | 状態・入力・イベントの型、乱数、季節処理、条件・効果 |
| `src/content/` | イベント、職業、年齢段階、調整値、原作と仮設定の区分 |
| `src/application/` | 時計、停止理由、ゲーム操作、保存との接続 |
| `src/storage/` | 保存データの形式・検証・読書き |
| `src/ui/` | React画面と表示部品 |
| `scripts/` | 複数人生の生成・診断集計 |
| `docs/` | 共通仕様、決定記録、開発工程、必要な原作出典メモ |

仕様の正本はリポジトリ内の文書に置き、チャットだけに変更を残さない。Codexを開発の中心とし、Claude Code等を利用する場合も同じ仕様・同じ基準でレビューする。常時の並行実装や二重実装は必須にしない。

`AGENTS.md`を用意するなら、作業ルール・検証コマンド・参照先を簡潔に記し、ゲーム仕様全文や一時的な進捗を重複して置かない。依存関係やコマンドは、実際の構成ができてから記載する。

## 13. Codexでの段階的な開発【提案】

各工程は、目的・対象外・確認条件を指定して依頼する。一度に全仕様を実装させず、動作を確認できる単位で進める。

| 工程 | 実装範囲 | 完了の確認 |
| --- | --- | --- |
| M0：仕様と土台 | リポジトリ、採用判断の記録、型、設定の骨格、実行環境 | ビルド・型確認が通り、未確定案が確定扱いになっていない |
| M1：コア | 出生、乱数、季節、最小の定期処理、選択待機・解決、死亡、少数の検証用イベント | UIなしで、固定入力による一生と再現確認ができる |
| M2：プレイ | 最小UI、自動進行、時限式モーダル・操作遮断、停止式、通常時の停止・速度・非表示対応 | ブラウザで出生から死亡まで遊べ、時限式の操作制限と復帰が機能する |
| M3：保存 | 自動保存、選択途中の復帰、死亡記録、版・破損・保存失敗、重複タブ対応 | 各停止地点から二重適用なく復帰できる |
| M4：内容と調整 | 教育、3系統の一般職、明示借入・返済と不利益、生活困窮、技能、職業追加枠と選択割合の調整、継続イベント、反復対策、バッチ診断 | 職業別の総件数・選択割合・年間密度と借金の不利益を試遊・集計し、矛盾を修正できる |

M1の選択待機・解決は実時計を持たず、外部入力として選択または期限切れを与える。M2でブラウザの時計を接続する。死亡・中断・一度だけの効果適用は後付けにしない。

各工程の報告は「変更点／確認したこと／未確認・制約／新しい暫定判断」とする。テストを実行できなかった場合は、通過したとは記載しない。大きな方針変更は変更理由と影響を示し、小さな実装判断は記録して進める。

寿命、死因、年齢段階・職業別の年間総件数、共通生活・職業・フレーバーの件数、選択件数・割合、抽選枠数・スキップ理由、同文反復率、資金・借金・生活困窮の分布、定期収入・イベント報酬・イベント支出の内訳、借入・返済・不利益イベント件数、未処理予約、検証中断を出力する。職業差は在職季節数も分母として比較し、在職期間の長さと頻度の差を区別する。補正が動いたことは平均回数だけで判断せず、候補・枠数・発生確率・選択割合の設定・重み自体も確認する。

資金の上限はゲームルールとして設けない。極端な増大は診断の対象にし、直ちにバグとは断定しない。バッチ生成が通っても、文章の自然さや選択の面白さまで保証されたとは扱わない。

## 15. 未決定事項と変更の記録

### 採用済みの判断【確定】

1. 時限式中は季節進行を待機させ、制限時間のみ進める。
2. 健康0を死亡条件の一つとし、事故等の直接死亡も認める。
3. P01では原作年表・テラ歴と接続せず、年齢と季節を用いる。

### 実装の詳細として引き続き提案のもの

- 時限式期限とクリックの競合境界、表示開始から期限開始までのタイミング。
