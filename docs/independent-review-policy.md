# 独立レビューの実施手順

運用版：v1.1（2026-10-22）。旧v0.1の追加案を共通ワークフローへ統合した版。レビュー人数の判断と例外は[共通ワークフロー](development-workflow.md)第3節、依頼・記録の型は[テンプレート](task-handoff-templates.md)を正本とする。本書は実施時だけ参照すればよい。

## 1. 目的と限界

WorkとClaudeなど、異なる担当によるレビューは見落としや誤指摘を比較できる。ただし資料不足や曖昧な要求による誤りは共有され得る。品質向上率や費用対効果は今回実測していない。

独立とは、当該実装・設計を主導していない担当が、他方の結論を見る前に初回評価を完成させること。同一モデルでも別の作業文脈なら候補になる。モデル変更だけで独立とはしない。実装者の再確認は自己レビューと記録する。

二重レビューの追加コストは、二人分の読解・検証、資料管理、結果統合、待ち時間。重要な変更に集中し、人数や賛成数より再現・テスト・コード上の根拠を優先する。

## 2. 同一スナップショットの準備

commit前のレビューでは、両者に同じZIP・中立的な依頼本文・仕様・受入条件を渡す。初回には双方が共通の重大リスクを確認できる資料を用意し、片方にしか重要な領域を見せない分担にしない。

| 内容 | 最低限含める情報 |
| --- | --- |
| manifest | タスクID、基準の完全なcommit SHA、snapshot ID、作成時点、収録・除外一覧、ファイルハッシュ、削除・改名・未追跡 |
| worktree/ | レビュー対象の最終状態。必要な周辺コード・型・設定・テスト・依存定義 |
| baseline/ | 同じ範囲の基準コード。初回commit前は基準なしと明記 |
| diffs/ | 基準から最終状態までの差分。stagedとunstagedを合わせ、新規・削除・改名・バイナリも識別 |
| specs/ | 適用仕様・承認済み変更・タスク・受入条件。未決事項も区別 |
| verification/ | 実行環境・コマンド・結果・未実施・制約。実装者の自己評価と事実を分離 |

基準は必ずしも現在のHEADとは限らない。選んだ基準から対象までを説明し、範囲を限定した場合は「対象範囲の完全差分」と明記する。差分だけで周辺の挙動を判断できなければ必要資料を追加する。

作成前に対象を固定し、作成中の変更を混ぜない。作業ツリーの変更・未追跡一覧と収録一覧を照合する。通常のdiffだけでは未追跡を拾えない。ignore対象の必要ソースも確認する。

機密・認証情報・個人データ・不要な生成物・依存フォルダ・.gitを除外する。除外は基準コード・差分・ログにも適用する。必要な情報を除外した場合は、値を漏らさず欠けた範囲と理由を明示し、可能ならダミーデータを用意する。秘密検出ツールの通過だけを安全の根拠にしない。

完成後にZIPの展開・一覧・ハッシュを確認し、ZIP全体のSHA-256を外部の依頼文へ添える。ZIP自身のハッシュをZIP内部へ埋め込まない。配布済みZIPは変えず、報告は外部へ保存する。各レビュアーは対象IDと、実行可能ならハッシュを照合し、照合できなかった点を記録する。

## 3. 初回評価の独立性と読み取り専用

- タスクの初回レビューには新しい会話を使い、両者が提出するまで他方の指摘・統合案・誘導的な評価を渡さない。
- 検証の事実と既知の制約は共有する。開発会話全文や実装者の「問題なし」という結論は初回資料へ混ぜない。
- 質問への回答は、評価を含まない同じ事実説明として双方へ渡し、補足を識別する。ソース・仕様変更や重大な資料追加は新しい対象／資料版として揃え直す。
- 初回報告を保存した後は相互の指摘を共有できる。「初回独立評価」と「比較後の再評価」を区別する。
- レビュー担当はコード変更・commit・push・deploy・リモート更新をしない。報告作成と、依頼で許可した隔離コピー上のローカル検証だけを行う。テストの副作用も確認する。
- 本番接続や秘密情報が必要なら未検証として返す。実装者のログを、自分が実行した結果として報告しない。

指示文だけで技術的な読み取り専用や完全な情報隔離が保証されるとは扱わない。可能なら固定ZIPで渡し、本体作業ツリーや書込み可能な接続へのアクセスを減らす。

## 4. Work Reviewの置き場所

| 配置 | 利点 | 留意点 |
| --- | --- | --- |
| 開発Project内の新しいWork | 仕様・共通ルールの参照と管理が容易 | 共有資料や指示に開発側・他方の評価が含まれる場合、初回判断へ影響し得る |
| 開発Project外の新しいWork | そのタスクへ渡す資料を揃えやすい | ZIP等の受け渡しが必要。外に置くだけでは完全隔離を保証しない |
| 別のレビュー専用Project内の新しいWork | 中立的なレビュー手順を再利用できる | 過去の指摘・統合結果を初回から共通参照させないよう管理する |

重要な二重レビューの初回はProject外またはレビュー専用Projectを候補にする。通常の単独レビューは開発Project内でもよい。配置だけで毎回大きな準備を増やさず、同じZIPを再利用する。

両サービスで実際の共有資料・指示・記憶等の条件を確認し、他方の結論が混入していると分かった場合は限界を記録する。必要なら共有条件を直して初回評価をやり直す。ユーザー環境の具体的な共有設定は今回検証していない。

## 5. 結果の統合と修正

統合担当は1タスクにつきメインChatまたは計画Workのどちらか1つ。両初回結果が揃ってから、同じコード・仕様・証拠を使って整理する。報告要約しか読めなければ、妥当性確認済みとはしない。

1. 対象ID・仕様版・補足・確認範囲を揃える。
2. 重複を統合し、原指摘IDを保持する。片方だけの指摘も残す。
3. 事実、仕様違反、影響の重大度、修正案を分け、到達経路・再現・テストで判断する。
4. 修正採用／不採用／追加検証／将来課題／ユーザーの仕様判断待ちに分け、理由を残す。
5. 採用ID・守る挙動・必要な検証をCodexへ渡す。

一方が見つけなかったことは反証ではなく、双方の一致も証明ではない。再現しない場合は入力・版・環境・モック・前提を比較する。解けない仕様判断を多数決にしない。第三のAIは自動追加せず、重大な争点が証拠追加後も残る場合に論点を絞って検討する。

修正後は新しい対象IDを付け、採用指摘と影響範囲を確認する。局所修正は原則1名の再確認でよく、毎回二重の全面レビューへ戻さない。新たな重要変更・広い設計変更があれば二重へ戻す。以前のレビューを新差分の承認として流用しない。

終了条件は必要な検証、採用指摘の解消、残課題の処置、対象の同一性、ユーザー受入れ。両者の意見が完全一致することは条件にしない。commit前にユーザーが対象一致を確認する。

## 6. 保存

初回報告は原本として残し、統合処置を既存タスクまたは1つの統合記録へ追記する。ZIPや巨大ログを毎回Gitへ入れる義務はないが、レビュー時点を追える基準・対象ID・ハッシュ・必要資料を保持する。commit後は必要な記録から対象SHAへ対応付ける。過去の結果を新しい初回レビューの共通資料へ自動投入しない。

Terra Lifeの統合担当・適用開始点・既存タスクのレビュー条件の保持は[project-context.md](project-context.md)第9章を参照する。過去の受入済み作業を本版だけを理由に再レビューしない。
