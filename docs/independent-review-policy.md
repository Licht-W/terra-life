# 独立レビューの実施手順

運用版：v1.2（2026-10-23）。v1.1へ独立レビューの利用量削減方針を統合。レビュー人数の判断と例外は[共通ワークフロー](development-workflow.md)第3節、依頼・記録の型は[テンプレート](task-handoff-templates.md)を正本とする。本書は実施時だけ参照すればよい。

## 1. 目的と限界

WorkとClaudeなど、異なる担当によるレビューは見落としや誤指摘を比較できる。ただし資料不足や曖昧な要求による誤りは共有され得る。品質向上率や費用対効果は今回実測していない。

独立とは、当該実装・設計を主導していない担当が、他方の結論を見る前に初回評価を完成させること。同一モデルでも別の作業文脈なら候補になる。モデル変更だけで独立とはしない。実装者の再確認は自己レビューと記録する。

二重レビューの追加コストは、二人分の読解・検証、資料管理、結果統合、待ち時間。重要な変更に集中し、人数や賛成数より再現・テスト・コード上の根拠を優先する。

Claudeの利用上限でレビューが長時間停止する状況を減らすため、両レビュアーの確認範囲を維持したまま、資料の重複、依存導入・環境修復、不要な全テスト再実行、冗長な報告を減らす。重要なコード・仕様・失敗記録の省略で負担を減らさない。

## 2. 同一スナップショットの準備

commit前のレビューでは、同じコードスナップショットから初回資料と必要時の補足資料を作る。両者に同じ初回ZIP・中立的な共通依頼本文・適用仕様・受入条件・確認範囲を渡す。実行可能な検証の条件は第4節に従い担当別に指定できる。片方にしか重要な領域を見せない分担にしない。資料量が少なければZIPを2つに分けることは必須にしない。

入口資料には目的、範囲、受入条件、読む順序、関連ファイル、既知の制約を簡潔に記載する。実装者の「問題なし」などの評価を混ぜない。以下は資料の役割を示す配置例であり、全項目を別フォルダや初回ZIPへ重複収録する義務ではない。

| 内容 | 最低限含める情報 |
| --- | --- |
| manifest | タスクID、基準の完全なcommit SHA、コードのsnapshot ID、作成時点、対象ファイルのハッシュ、収録・除外一覧、削除・改名・未追跡。配布資料版はコード識別と分ける |
| worktree/ | 対象の変更後コードの原文、判断に必要な周辺コード・型・設定・関連テスト・依存定義。要約だけで代用しない |
| baseline/ | 比較に必要な基準コード。大量なら補足へ回せる。初回commit前は基準なしと明記 |
| diffs/ | 基準から最終状態までの読解用差分。stagedとunstagedを合わせ、新規・削除・改名・バイナリも識別 |
| specs/ | 適用仕様・承認済み変更・タスク・受入条件。未決事項も区別 |
| verification/ | 短い検証一覧（環境・コマンド・結果・対象ID）と判断に必要な成功・失敗の証拠。原因未確定事項、未検証範囲、計装の有無・実行条件の違いも初回に残し、事実と自己評価を分離 |

基準は必ずしも現在のHEADとは限らない。選んだ基準から対象までを説明し、範囲を限定した場合は「対象範囲の完全差分」と明記する。差分だけで周辺の挙動を判断できなければ必要資料を追加する。

大量の変更前コード、途中の全実行履歴、重複した出典情報、診断画像、再実行用の追加資料は、判断への必要性を見て補足へ回せる。初回資料に収録しない範囲と、補足の内容・参照方法を明記する。同一の周辺コードを変更前・変更後で重複収録したり、複数種類の差分を毎回全文読ませたりすることを避け、比較に必要な情報は参照可能にする。既知の失敗や重要な制約を補足だけへ隠したり、成功ログだけを選別したりしない。

作成前に対象を固定し、作成中の変更を混ぜない。作業ツリーの変更・未追跡一覧と収録一覧を照合する。通常のdiffだけでは未追跡を拾えない。ignore対象の必要ソースも確認する。

機密・認証情報・個人データ・不要な生成物・依存フォルダ・.gitを除外する。除外は基準コード・差分・ログにも適用する。必要な情報を除外した場合は、値を漏らさず欠けた範囲と理由を明示し、可能ならダミーデータを用意する。秘密検出ツールの通過だけを安全の根拠にしない。

作成側は収録漏れ、対象ファイルのハッシュ、差分、展開後の整合性を確認する。コードのsnapshot ID・基準commit・対象ファイルのハッシュと、配布資料版・ZIPハッシュは別の識別情報として管理する。完成したZIP全体のSHA-256は外部の依頼文へ添え、ZIP内部へ自身のハッシュを埋め込まない。ZIPを再構成した場合は同じコードでも新しい配布資料版とZIPハッシュを付け、元の配布物を上書きしない。報告はZIPの外部へ保存する。

各レビュアーは対象IDと、実行可能ならハッシュを照合し、照合できなかった点を記録する。整合性確認は可能なら一括処理し、結果と不一致だけを出力する。巨大なmanifestや全ハッシュを会話へ全文表示する必要はない。

## 3. 初回評価の独立性と読み取り専用

- タスクの初回レビューには新しい会話を使い、両者が提出するまで他方の指摘・統合案・誘導的な評価を渡さない。
- 検証の事実と既知の制約は共有する。開発会話全文や実装者の「問題なし」という結論は初回資料へ混ぜない。
- 質問への回答や追加の仕様・コード・検証資料は、評価を含まない同じ事実説明として双方へ渡し、補足を識別する。コード・仕様変更は新しい対象ID、資料追加・再構成は新しい配布資料版として揃え、どの資料版で判断したか記録する。
- 両者の初回報告が揃い保存された後は相互の指摘を共有できる。「初回独立評価」と「比較後の再評価」を区別する。
- レビュー担当はコード変更・commit・push・deploy・リモート更新をしない。報告作成と、依頼で許可した隔離コピー上のローカル検証だけを行う。テストの副作用も確認する。
- 本番接続や秘密情報が必要なら未検証として返す。実装者のログを、自分が実行した結果として報告しない。

指示文だけで技術的な読み取り専用や完全な情報隔離が保証されるとは扱わない。可能なら固定ZIPで渡し、本体作業ツリーや書込み可能な接続へのアクセスを減らす。

## 4. 担当別の実行条件とWork Reviewの置き場所

### Workのレビュー

静的レビューと提供された検証記録の照合を行い、必要に応じて、許可された隔離環境で対象を絞った実行検証を行う。全テスト再実行や環境構築を毎回必須にしない。環境制約があれば未実施として明記し、環境修復を目的化しない。

### Claudeのレビュー

静的レビューと提供された検証記録の照合を基本とし、依存インストール、環境修復、全テスト再実行は行わない。ZIP展開・ハッシュ照合・差分比較など、既存環境で可能な資料確認は行える。

指定範囲の変更後コードを中心に読み、必要に応じて変更前コード・差分・依存先へ確認を広げる。全ファイルの一括表示、同じ資料の反復読解、不要な外部検索を避ける。動的確認が必要な疑いは発生条件・コード上の根拠・最小限の確認方法を報告し、推測で不具合確定や検証済みにしない。

### Work Reviewの置き場所

| 配置 | 利点 | 留意点 |
| --- | --- | --- |
| 開発Project内の新しいWork | 仕様・共通ルールの参照と管理が容易 | 共有資料や指示に開発側・他方の評価が含まれる場合、初回判断へ影響し得る |
| 開発Project外の新しいWork | そのタスクへ渡す資料を揃えやすい | ZIP等の受け渡しが必要。外に置くだけでは完全隔離を保証しない |
| 別のレビュー専用Project内の新しいWork | 中立的なレビュー手順を再利用できる | 過去の指摘・統合結果を初回から共通参照させないよう管理する |

重要な二重レビューの初回はProject外またはレビュー専用Projectを候補にする。通常の単独レビューは開発Project内でもよい。配置だけで毎回大きな準備を増やさず、同じZIPを再利用する。

両サービスで実際の共有資料・指示・記憶等の条件を確認し、他方の結論が混入していると分かった場合は限界を記録する。必要なら共有条件を直して初回評価をやり直す。ユーザー環境の具体的な共有設定は今回検証していない。

## 5. 結果の統合と修正

### 初回報告

対象ID・判断に用いた配布資料版、確認範囲、指摘と根拠、実施した検証、未確認事項、受入れに関わる未解決点を中心に簡潔にする。指摘にはID・場所・発生条件・影響・根拠・重大度・確度・修正方向を残す。問題のない各領域の長い解説は必須にせず、重大な指摘の件数は制限しない。

判定は「受入れ可の意見／修正後に受入れ可の意見／資料・検証不足で判断保留」などとし、利用上限等による確認未完了を承認扱いにしない。レビュアーの判定は受入れへの意見であり、最終受入れはユーザーが行う。

### 統合と追加検証

統合担当は1タスクにつきメインChatまたは計画Workのどちらか1つ。両初回結果が揃ってから、同じコード・仕様・証拠を使って整理する。報告要約しか読めなければ、妥当性確認済みとはしない。

1. 対象ID・仕様版・補足・確認範囲を揃える。
2. 重複を統合し、原指摘IDを保持する。片方だけの指摘も残す。
3. 事実、仕様違反、影響の重大度、修正案を分け、到達経路・再現・テストで判断する。
4. 修正採用／不採用／追加検証／将来課題／ユーザーの仕様判断待ちに分け、理由を残す。
5. 採用ID・守る挙動・必要な検証をCodexへ渡す。

一方が見つけなかったことは反証ではなく、双方の一致も証明ではない。再現しない場合は入力・版・環境・モック・前提を比較する。解けない仕様判断を多数決にしない。第三のAIは自動追加せず、重大な争点が証拠追加後も残る場合に論点を絞って検討する。

初回結果の提出後、統合担当が必要な追加検証をWorkまたはCodexへ依頼する。追加の検証資料も双方へ共有し、判断に用いた版を残す。Codexの追加検証は実装側の検証として記録し、Claudeによる独立再実行とは扱わない。

修正後は新しい対象IDを付け、採用指摘と影響範囲を確認する。局所修正は原則1名の再確認でよく、毎回二重の全面レビューへ戻さない。新たな重要変更・広い設計変更があれば二重へ戻す。以前のレビューを新差分の承認として流用しない。

終了条件は必要な検証、採用指摘の解消、残課題の処置、対象の同一性、ユーザー受入れ。両者の意見が完全一致することは条件にしない。commit前にユーザーが対象一致を確認する。

## 6. 保存

初回報告は原本として残し、統合処置を既存タスクまたは1つの統合記録へ追記する。ZIPや巨大ログを毎回Gitへ入れる義務はないが、レビュー時点を追える基準・対象ID・ハッシュ・必要資料を保持する。commit後は必要な記録から対象SHAへ対応付ける。過去の結果を新しい初回レビューの共通資料へ自動投入しない。

Terra Lifeの統合担当・適用開始点・既存タスクのレビュー条件の保持は[project-context.md](project-context.md)第9章を参照する。過去の受入済み作業を本版だけを理由に再レビューしない。

## 7. 利用量削減方針の試行と見直し

次に開始する二重レビューから試行する。進行中タスクの約束済みレビュー条件や完了済みの受入判断は自動変更しない。今回はレビュー対象範囲を狭めない。

なお上限に達する場合は、資料・作業の重複、タスク分割、Claudeの対象限定を順に検討する。将来Claudeの対象を重要範囲へ限定する場合は、対象と残るリスクを示してユーザーの明示的な判断を得て、「全体の単独レビュー＋重要範囲の二重レビュー」と記録する。全体を二重レビューしたとは扱わない。

試行後は上限到達回数、追加資料の往復、重要範囲を確認しきれたかを簡単に振り返る。新しい管理表や厳密なトークン計測は必須にしない。
