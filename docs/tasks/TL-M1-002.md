## 1. 採用済みの範囲と判断

### 1.1 今回の出生項目

- 国：ヴィクトリア。種族：フェリーン。P01の採用方針に従って固定する。
- 抽選する情報：家庭の経済状況、健康・精神・資金・知識・人脈の基本5ステータス。
- 開始前に出生候補を再抽選できる。開始後の出生条件は固定する。

- 親の職種、詳細な家族構成、技能、裏適性、居住環境の新しい区分・抽選は今回扱わない。

### 1.2 家庭の経済状況：採用した5区分

| 区分 | 意味 |
| --- | --- |
| 日々をしのぐ暮らし | 食料・住居・医療の確保にも苦労する、生活基盤が非常に弱い家庭 |
| 切り詰めた暮らし | 基本的な生活は維持しているが、経済的な余裕がほとんどない家庭 |
| つつましい暮らし | 日常生活はおおむね安定しているが、大きな支出には工夫が必要な家庭 |
| ゆとりのある暮らし | 安定した経済基盤があり、教育・治療などにも比較的余裕がある家庭 |
| 裕福な暮らし | 十分な蓄えや経済基盤を持ち、高額な支出や継続的な支援も可能な家庭 |

名称・意味はユーザー指定のまま採用する。先に提示した「困窮／一般／裕福」の3区分案は未採用であり、現行定義に使わない。内部キーの命名は技術判断だが、日本語表示名・意味との対応を明示する。

これはTerra Life独自の区分で、原作の公式階級・人口構成ではない。移動都市内・地方農村・荒野の集落などの居住環境とは別概念であり、家庭区分から居住環境を自動決定しない。

### 1.3 家庭環境と本人の資金・能力

- 家庭の経済状況は出生時の環境を表す独立した情報。本人の資金、家族の総財産、身分、技能とは区別する。
- 家庭区分を本人の初期資金の抽選条件として利用できる。ただし、区分から資金が一意に決まる固定額方式にはしない。今回の検証用設定でも、各家庭区分に複数の正の重みを持つ初期資金候補を用意して確認する。
- **今回の家庭区分による出生時補正は初期資金だけに限定する。** 健康・精神・知識・人脈の候補・分布へ家庭別の補正を加えない。家庭区分から能力や将来を固定しない。
- 出生後、裕福であることだけを理由に本人の資金を定期加算しない。本人の定期収入・イベント収入・支出等はD07に従い、家庭からの仕送り・援助は必要な明示イベントで扱う。これらの実処理は今回作らない。
- 本人の資金増減から家庭区分を自動変更しない。
- 出生時の区分は履歴として保持する。将来、明示イベントで家庭の現在の状況が変わっても出生時の事実を上書きしない。ただし、現在区分の変更API・履歴機構・イベントは今回実装しない。
- ユーザーの「初期資金80」は説明例であり、固定額・正式バランス・資金上限の採用ではない。

### 1.4 数値委任と保留

出生確率、初期値の候補・分布、資金の候補・家庭別の重み等は、D09に従って今回の検証用にAIが仮設定できる。設定値・用途・理由・見直し条件を記録する。正式バランスや原作確認済みデータへ昇格させない。

資金は0以上の整数ポイント。資金上限の有無・100上限・超過時の処理は引き続き未決であり、今回の初期資金表の最大値をゲーム上の残高上限として実装しない。家庭区分による能力補正、教育・職業・生活への将来の具体効果、家庭変化の仕組みも今回新設しない。

## 3. 実装範囲と契約

### A. 最小のデータ定義と出生抽選

1. 第1章の5区分を、安定した内部キー・表示名・意味で定義する。候補設定と抽選処理を分け、原作事実・正式バランスと混同しない検証データとして扱う。
2. 基本4値（健康・精神・知識・人脈）は家庭区分によらない候補設定、初期資金は家庭区分を条件に選べる候補設定として表す。今回必要な小さな候補・重みの定義から始め、汎用ルール言語や任意コードの評価を作らない。
3. 各項目の検証用の具体分布は数値委任の範囲で選び、相関・分布の自然さを正式な出生モデルとして確定しない。家庭区分と能力の直接補正、隠れた職業・将来の決定を入れない。
4. 既存`src/core/random.ts`を利用する。基準時点の公開APIは`createRandomStreams`、`copyRandomState`、`nextUint32`、`uint32ToUnit`等。今回のためにPRNG・初期化・jump・系列割当てや既存固定値を書き換えない。
5. 出生抽選・再抽選が消費するのは`birth`だけ。`life`と`flavor`の値・後続列を変えない。国・種族の固定値、読出し・コピー・開始確定・診断記録に、不要な乱数消費を加えない。
6. 候補の順序と項目の抽選順を明示し、同じデータ版・シード・再抽選操作で同じ候補列と状態になるよう固定する。候補順をデータとして保持し、不定な列挙順・locale・時刻等に依存させない。家庭区分を4値の抽選に参照しないことを、実装構造とテストから確認できるようにする。
7. D04の採用済み抽選方針に従い、0重みを選ばず、実効候補1件では抽選乱数を消費しない。実効候補が複数なら固定順の累積重みで1回抽選する。重み合計0・候補なしは不正設定として扱い、出るまで再抽選・既定候補への代替はしない。
8. 家庭区分が変われば必ず資金が増減する、裕福なら常に他区分以上になる、候補範囲が区分間で重ならない、といった規則は採用していない。検証値の選び方をそうしたゲーム契約へ昇格させない。

### B. 出生候補・再抽選・開始確定

- 開始前の候補段階と、開始後の出生確定段階を区別する。型・関数名は技術判断とする。詳細なGameState、季節カーソル、イベント契約を先行設計しない。
- 最初の候補生成、開始前の再抽選、現在の候補を採用して開始確定する操作を用意する。再抽選では現在の出生候補全体を更新する。過去候補の一覧・選び直しUI、項目ごとの固定や個別再抽選は追加しない。
- 再抽選回数は初回候補を0とし、成功した再抽選ごとに1増やす。シードと同じデータから「初回＋その回数の再抽選」で候補列を再現できるようにする。失敗した操作や読出しで回数を変えない。
- 開始確定は候補をそのまま採用し、再抽選・追加抽選をしない。開始後の状態へ再抽選・再開始操作を送っても拒否し、確定済みの出生条件・乱数・回数を変えない。外部副作用のない純粋関数として、同じ開始前入力を別々に評価した結果の一致と、開始後状態への操作拒否を区別する。
- 呼出し前の状態・設定を変更しない。確定後の出自が候補や設定への共有参照を通じて書き換わらないようにする。JSON往復できる値を基本とし、メモリ上のコピーから同じ候補列を継続できるようにする。
- 開始時に、正規化シード、再抽選回数、国・種族・出生時家庭区分・基本5値、今回適用したルール／出生データ・調整値／乱数方式の識別情報、開始時の3系列状態を再現用情報（Origin相当）へ保持する。乱数方式の識別名・版文字列等は実際の契約を示す最小限を選び、正式セーブ形式・移行方式まで決めない。
- 開始時の初期値スナップショットと、その後変化する人物の値を混同しない。今回の出自情報に記録した初期資金・出生家庭区分を、将来の人物の現在値で上書きする構造にしない。現在値を更新する経済・家庭変化APIは今回作らない。
- 0歳春の開始条件を保持できればよく、年齢・季節の進行、出生の表示文・人生ログの追加、職業・成長段階・家族ID等の未使用情報は先行追加しない。

### C. 不正データと失敗時の保持

- 設定の不足・重複ID・未知の家庭区分、家庭別資金候補の欠落、不正な重み・数値・シード・乱数状態、段階に合わない操作等を理由付きで検出する。
- 非有限値・負の重み・非有限または0以下の合計、非整数・負の資金、JavaScriptで整数を正確に表せない資金等を黙って補正しない。数値精度の検証は技術上の制約であり、ゲーム上の資金上限とは区別する。
- 基本4値は仕様書の暫定0〜100を検証設定の範囲として扱い、将来の能力上限や丸め・clampの一般契約を新設しない。今回は検証用の整数候補を選べるが、基本4値の小数可否をゲーム全体の仕様として追加確定しない。
- 生成・再抽選・開始の処理単位で、候補・回数・乱数等をまとめて返す。不正により失敗した場合は途中の抽選消費・候補だけを残さず、入力の最後の正常状態を保持する。設定が不正でも再抽選で救済せず、原因を返す。
- 初期化前に失敗した場合は、存在しない正常状態を捏造しない。ゲーム内死亡・黙った初期化・無関係な既定値への代替にしない。
- 今回の出自モジュールは初期データの抽選と確定に限定し、人物の生存フラグ・死亡処理を作らない。健康0は既存仕様上の死亡境界であり、検証を通すために正当な数値0を不正扱いしたり、最低1へ補正したりしない。生存中として健康0を保証する契約も作らず、開始後の死亡判定は該当コア処理のタスクで扱う。
- D08を満たす失敗表現は最小の結果型等で具体化してよい。ゲーム全体の診断停止システム、保存上書き防止の接続、ブラウザI/Oは今回実装しない。
