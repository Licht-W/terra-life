## 1. 元の依頼・今回の合意

目的：開始確定済みの出生状態から、季節を進め、中断・再開・健康0による死亡を扱える純粋な最小コアを作る。

今回採用した入力識別はlifeIdとexpectedRevision。対象人生が違う入力、古い入力、成功済み入力の再送による二重進行を防ぐ。成功した状態遷移ではrevisionを更新し、不受理では変更しない。識別子の受け渡し・具体的な型名・関数分割は、実時計や乱数への新規依存を加えず実装担当が決め、理由を記録する。

実装範囲：

- 開始確定済みの出生状態から進行状態への接続。Origin・人物・乱数状態を独立したコピーとして保持する。
- 0歳春をseasonIndex=0とし、年齢はfloor(seasonIndex / 4)、季節はseasonIndex % 4から求める。
- 季節内の処理位置を保持し、季節完了時だけseasonIndexを1増やす。途中状態からの再開を検証できる最小限の段階を設ける。
- 健康0を確認したら、その年齢・季節で死亡を一度だけ確定し、季節更新を止める。出生時の健康0も補正しない。
- 入力不受理、診断停止、正常な死亡を区別する。診断停止では最後の正常状態と原因を保持し、無断補正・初期化・再抽選で続行しない。
- JSON往復した途中状態から同じ入力列で継続できる。
- イベントのない季節に空の人生記録・季節見出し用レコードを追加しない。

季節処理は今回実装する部分に限定し、将来の全処理段階を空の仕組みとして大量に作らない。

範囲外：イベントの提示・選択・直接死亡効果・抽選枠・予約・連鎖・冬のフレーバー補充、経済、成長・老化、実時計、UI接続、ブラウザ保存、一生生成、依存追加。

空イベント経路は基盤の限定検証であり、「生存年には最低1件の記録を持つ」という完成時の仕組みを変更・撤回しない。冬の補充は後続で実装する。資金上限や能力値の新しい上限・補正式は決めない。既存の出生抽選、乱数方式・消費順、検証用分布を変更しない。

## 3. 実装契約・判断

今回具体化した契約は次のとおり。正式保存形式・互換性・移行方式を採用するものではない。

- 実体は`src/core/progression.ts`。`connectBirth(startedBirth, lifeId)`、`advanceCore(state, input)`、`copyCoreState(unknown)`を公開する。接続は開始済み段階と初期スナップショットの一致を検証し、revision=0、check-healthから開始。健康0は補正せず、最初の有効な進行入力で死亡する。
- lifeIdは呼出し側から渡す空白だけではない文字列。別人生に同じIDを割り当てない責任は呼出し側にある。時計・乱数・グローバルカウンターに依存せず、同一入力から同一出力を返すための選択。コアは世界全体でのID一意性・永続的ロックを保証しない。同じ旧状態を別々に評価すれば同じ結果になる純粋関数であり、呼出し側は受理された最新状態へ差し替える。
- 入力は`{kind: 'advance', lifeId, expectedRevision}`。出生接続後の進行状態に対し、対象とrevisionが一致する有効入力だけを受ける。健康確認・季節完了・死亡確定ごとにrevisionを1増やす。拒否結果に新状態を含めず、呼出し側が保持する現状態は不変。入力の形が不正・不一致・終了済みなら計算前に拒否する。
- 季節は`check-health`→`complete-season`→次季節の`check-health`の2段階。前者で健康を確認し、後者で健康を再確認して季節完了だけを行う。stageは次に実行する位置であり、JSON往復しても先頭へ戻さない。完了後だけseasonIndexを1増やす。段階を示すだけの人生記録は作らない。
- 健康0での正常な死亡は`status: 'dead'`と1件の死亡記録で表す。死亡記録にcause=health-zero、seasonIndex、floor(index/4)のage、index%4のseasonを保持する。別のdeathフィールドや生死フラグを重ねず、既存の死亡記録と人物の健康・年代の整合を境界で確認する。死亡後の入力は拒否する。
- 結果区分は`accepted`／`rejected`／`invalid-state`／`diagnostic-stop`。有効な数値0を不正とせず、精神0・資金0を死亡へ変換しない。不正な外部入力状態は`invalid-state`と原因だけを返し、lastNormalを捏造しない。正常な構造の状態で遷移計算が成立しない場合にだけ診断停止を返す。
- 診断停止は進行状態と分けた`DiagnosticStop`包絡（status、lastNormal、cause）。lastNormalは失敗した遷移直前の独立コピーで、revision・季節・段階・人物・乱数・履歴を変更しない。causeはcode・message・lifeId・revision・seasonIndex・stage。診断への移行を正常処理成功に数えず、revisionも消費しない。診断包絡はJSON再読込できるがadvanceは拒否し、再開・自動修復APIは作らない。
- 今回計算が失敗する境界はrevision、季節完了時のseasonIndexの安全整数限界。revisionを更新できない場合は死亡確定も含めて正常遷移を返せないため診断停止する。seasonIndex限界でも健康確認は可能で、健康0の死亡は季節加算を要しない。これはJS数値精度の制約であり、ゲーム内の寿命・資金・検証用総処理回数の上限ではない。
- 境界検証は対応版、段階・status、空でないID、非負安全整数のカウンター・資金、既存の暫定0〜100の基本4値（有限、小数可）、Origin、3乱数系列、履歴・死亡情報・診断原因の整合を扱う。既存出生の版・シード・家庭等の検証は非消費のcopyBirthDraftを利用し、再抽選しない。未知の追加フィールドは採用せず捨て、既知フィールドから独立コピーを作る。
- 構造の妥当性検証と、開始からその状態へ本当に到達した証明は別。全人生のリプレイ、外部データの真正性・改ざん防止、カウンターの全履歴照合、M3の正式保存・移行は行わない。後半季節の健康0・整数限界のテストは外部スナップショットを直接構築するが、製品へ任意状態変更APIを追加しない。
- 進行ルール識別は`tl-m1-003-empty-season-1`。今回の空イベント検証経路を明示するために付与し、将来イベントや定期処理を実装した版との無条件な再現・互換性を約束しない。生存年最低1記録の完成時契約は維持し、冬の補充は未実装。
